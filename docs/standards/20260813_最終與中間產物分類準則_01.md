# 最終產物與中間產物的分類準則

## 這份準則要解決什麼

`research/` 已累積到 **99 個專案目錄、7.36 GB、2,613 個 tracked 檔案**，其中絕大多數
沒有任何狀態標記。交接時最常被問、也最難回答的問題是：

> 這個目錄還有用嗎？可以刪嗎？

憑感覺回答的問題不在於會答錯，而在於**不可重現** —— 同一個目錄，今天問和明天問、
問人和問 AI，會得到不同答案。所以這份準則把判斷寫成可執行的規則：
`scripts/handoff/classify_artifacts.py`。同樣的輸入永遠得到同樣的分類，
而且可以隨時重跑來偵測漂移。

---

## 1. 這是第四個軸，不是第四套分類法

本 repo 已有三個正交的軸，定義在
`docs/data_specs/20260414_output資料信任度與生命週期_01.md`：

| 軸 | 值域 | 回答的問題 |
|---|---|---|
| **信任度** | CURRENT / PRE-FIX / SUPERSEDED / DEPRECATED | 這個結果**可不可信** |
| **生命週期** | in_progress / validated / finalized | 這個結果**還會不會改** |
| **刪除安全度** | SAFE_DELETE / LOW_RISK / KEEP | 刪掉它**會不會出事** |

本準則新增的是**處置 bucket**，回答第四個問題：**這個東西該放在哪裡**。
它是前三軸的函數，不是替代品 —— 例如 `DEPRECATED` 這個信任度值會直接
override 決策樹的結果（見 §3 保護規則）。

---

## 2. 決策樹：四個問題，第一個 YES 就定案

```
Q0  量得出體積嗎？
    → 量不出來 → MANUAL（專案級處置，不是逐檔判斷能解決的）

Q1  有人以「路徑形式」引用它嗎？   research/<名稱> 出現在任何 tracked 文件中
    → 有 → 【最終】 ≤10 MB 走 A（進 git）／ >10 MB 走 B（留磁碟＋登錄路徑）

Q2  30 分鐘內重建得出來嗎？        有 tracked builder ＋ 已有檔案進 git
    → 是 → 【中間】走 C（觀察期後刪）

Q3  檔名命中中間物 pattern 嗎？    *.tmp-* / *_debug.* / verification-failure
                                   / *.bak / *.pyc / *_v<N>.py / *.stdout / *.stderr
    → 是 → 【中間-立即】走 D（直接刪）
       但若另有「裸名提及」→ 降級為 C，走觀察期而不直接刪

四個都不是 → MANUAL，進人工裁決佇列。**不要猜。**
```

### bucket 的意義與對應動作

| bucket | 意義 | 動作 |
|---|---|---|
| **A** | keep-in-git | 進版本控制，接手者 clone 就有 |
| **B** | keep-on-disk-indexed | 留在本機磁碟，**路徑登錄進 handoff manifest**，git 內只留指標 |
| **C** | archive-then-delete | 搬進 quarantine → 觀察期 → 壓縮 → 確認無殘留引用才刪 |
| **D** | delete-now | 中間物 pattern 且無人提及，可直接清 |
| **MANUAL** | 人工裁決 | 規則不適用，需要人看過才決定 |

## 3. 兩個刻意的設計偏誤

### 3.1 保守偏誤：寧可多留，不可誤刪

Q1 只要有**一個**外部路徑引用就判「最終」。這是刻意的：

> 誤判成「最終」的代價是多留一份檔案。
> 誤判成「中間」的代價是刪掉還有人在引用的東西。
> 兩者不對稱，所以規則偏向留。

### 3.2 `DEPRECATED` 永遠不進 D

已知錯誤的結果**不能靜默刪除**。刪掉它會讓「這個結論是錯的」失去物證，
未來有人重新提出同一個想法時，就沒有證據說明為什麼當初否決。

規則：`DEPRECATED` 一律歸 B，並留 `ARCHIVED.md` redirect 說明它為什麼被否決、
被什麼取代。

## 4. 引用強度必須分強弱，否則 ledger 會退化成「全部保留」

`research/` 裡有 `subclonal_reconstruction`、`feature_layered_observation`、
`external_tools`、`data_registry`、`igv_sessions` 這類**通用名稱**目錄 ——
它們同時也是這個 repo 的日常詞彙與 skill 名稱。

第一版只比對裸名，結果任何一篇談到「subclonal reconstruction」的文件都被算成
「有人在引用這個目錄」，於是幾乎所有東西都變成最終產物：**C=1、D=0**。
ledger 退化成「全部保留」，等於沒有分類。

修正後區分兩種引用：

| 強度 | 判準 | 用途 |
|---|---|---|
| **strong** | 該行含 `research/<名稱>` | 明確指向這個目錄，用於 Q1 判定 |
| **weak** | 只出現裸名 | 可能只是在講這個概念，**不足以判定為最終產物**，但足以阻止「直接刪」 |

實測差異（來自 ledger）：

| 專案 | strong | weak | 說明 |
|---|---:|---:|---|
| `subclonal_reconstruction` | 3 | 28 | 28 處裸名多半是在談概念；真正的路徑引用只有 3 處 |
| `igv_sessions` | 6 | 12 | |
| `external_tools` | 2 | 10 | |
| `feature_layered_observation` | 15 | 3 | 同名 skill，但路徑引用反而更多 |

## 5. 全 99 個專案的分類結果

資料來源：`docs/handoff/20260813_實驗室交接_01/research_project_ledger.tsv`

| bucket | 專案數 | 磁碟體積 | tracked 檔數 |
|---|---:|---:|---:|
| A keep-in-git | 62 | 0.12 GB | 551 |
| B keep-on-disk-indexed | 29 | 7.23 GB | 1,720 |
| C archive-then-delete | 2 | ~0 | 12 |
| D delete-now | 0 | 0 | 0 |
| MANUAL | 6 | ~0 | 330 |
| **合計** | **99** | **7.36 GB** | **2,613** |

### 這個分佈本身就是結論

**D = 0、C = 2。** 清理空間不在「刪掉整個研究專案」——
99 個專案裡有 91 個被路徑引用著，它們是真的還在被使用。

真正的整理空間在兩處：

1. **B 的 7.23 GB** —— 這些是最終產物沒錯，但體積不該進 git。
   處置是「留磁碟 + 在 manifest 登錄路徑」，而不是刪除。
2. **2 個病態目錄** —— 見 §6。

## 6. 兩個病態目錄：連體積都量不出來

`paired_priority_bug_audit` 與 `tsg_promoter_asm_reviewer` 在 10 秒內
**`du -sb` 跑不完**，因此被標記為 `PATHOLOGICAL`。

這不是量測工具的問題，而是分類訊號本身：

> 一個連體積都量不出來的目錄，本質上就不可能是「進 git」的候選。
> 量測逾時本身就是有意義的分類結果。

背景：`paired_priority_bug_audit/` 的結構是每個 region 一個子目錄，
各含 `metadata.txt` / `reads.tsv` / `methylation.csv` / `distance_matrix_*.csv` / `*.png`
（即 `.claude/rules/output-structure.md` 描述的 ISM 標準輸出格式）。
在全基因組尺度上跑，就會產生數量級失控的檔案數。實測：對整個 `research/`
做 `find -type f` 在中斷前已產出 **356 萬行**仍未跑完。

**這兩個目錄需要專案級處置**（整批搬移／壓縮成單一 archive），
不是逐檔分類能解決的。它們也是 P7 安全清理的首要目標。

⚠ 兩者合計仍有 **322 個檔案已進 git**（64 + 258），
這部分在 `git rm --cached` 前必須先確認沒有文件引用它們。

而且它們**被引用得很兇** —— `tsg_promoter_asm_reviewer` 有 91 處路徑引用、
`paired_priority_bug_audit` 有 68 處，在全 repo 排第 2、第 3
（第 1 是 `autoresearch` 的 184 處，那是證據鏈目錄，性質不同）。
所以這兩個目錄**不是可以整包丟掉的垃圾**，而是「內容有用但組織方式失控」——
處置方向是**重整結構**（把 per-region 輸出壓成單一 archive 或改存 HDF5/parquet），
不是刪除。

## 8. 怎麼重跑、怎麼偵測漂移

```bash
# 重建 inventory 快取（慢，目錄結構有變動時才需要）
python3 scripts/handoff/classify_artifacts.py --scan

# 產生 ledger（快，約 10 秒）
python3 scripts/handoff/classify_artifacts.py \
    -o docs/handoff/20260813_實驗室交接_01/research_project_ledger.tsv

# 漂移偵測：重新分類並與既有 ledger 比對，不一致 exit 1
python3 scripts/handoff/classify_artifacts.py \
    --check docs/handoff/20260813_實驗室交接_01/research_project_ledger.tsv
```

**兩階段設計是必要的，不是權宜。** 第一版用 `os.walk` 走整個 `research/`，
跑超過 10 分鐘還沒完（見 §6）。拆成 `--scan`（慢，偶爾跑）與產生 ledger（快，可常跑）
之後，日常檢查只要 10 秒，才有可能真的被納入流程而不是寫完就沒人跑。

`--check` 是這份 ledger 不會腐爛的機械保證。本 repo 已有數份 INDEX
就是因為「寫完之後再也沒人對過」而失效 —— 把 `--check` 接進 CI 或
handoff 驗收腳本，就不會重蹈覆轍。

## 9. 已知限制

| 限制 | 影響 | 緩解 |
|---|---|---|
| Q2 的「30 分鐘內重建得出來」用「有 tracked builder」當代理指標 | 有 builder 不等於輸入資料還在 | C bucket 一律走觀察期，不直接刪 |
| 引用偵測只掃 tracked 檔案 | 未進 git 的筆記若引用了某目錄，偵測不到 | 保守偏誤已涵蓋（傾向留） |
| 引用偵測跳過 `docs/methodology/_assets/` | 該目錄有 66 MB 單一 HTML，掃它拖慢且無意義 | 該目錄是資料資產，不是敘述文件，不會有引用關係 |
| `PATHOLOGICAL` 門檻是固定的 10 秒 | 機器負載高時可能誤判 | 重跑 `--scan` 即可；誤判方向是「歸 MANUAL」，安全 |
| bucket 只到專案層級，不到單檔層級 | 一個 A 專案裡仍可能混著中間檔 | §2 的 Q3 pattern 可獨立套用在單檔上 |

## 10. 速查卡

```
拿到一個檔案或目錄，問四次：

Q0 量得出體積嗎？        量不出來 → MANUAL（專案級處置）
Q1 有人用路徑引用它嗎？   有 → 【最終】≤10MB 進 git(A) / >10MB 留磁碟+登錄(B)
Q2 30 分鐘內重建得出來？  是 → 【中間】觀察期後刪(C)
Q3 命中中間物 pattern？   是 → 【中間-立即】直接刪(D)
                              但有裸名提及 → 降為 C

四個都不是 → 人工裁決，不要猜

鐵則：DEPRECATED 不能靜默刪，一律留 ARCHIVED.md redirect
      —— 刪掉檔案會讓「這個結論是錯的」失去物證
```
