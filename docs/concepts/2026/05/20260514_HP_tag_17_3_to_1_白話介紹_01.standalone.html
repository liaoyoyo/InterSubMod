17.3:1 不是 code 寫死的常數，而是「somatic 票天生偏一邊」乘上「getVote 看到 1 票就 break、germline 完全被無視」兩個機制疊加後在 BAM 統計上的湧現值。

0.TL;DR — 一眼看完

跑完 baseline longphase-to 後，把輸出 BAM 的 HP tag 統計起來：HP1 系列 reads 數 ÷ HP2 系列 reads 數 ≈ 17.3 倍。Tumor 樣本理論上應該接近 1:1，這個 17 倍偏移是 bug 造成。bug 在 HaplotagProcess.cpp:506-530 的 getVote() 函式：vector pair 排序 + break early 兩個小設計選擇疊在一起，讓 1 票 somatic 就能蓋過 5 票 germline。

1.17.3:1 不是寫死在 code 裡的常數

17.3:1 是跑完統計出來的實測值，不是程式碼裡的某個變數。在 baseline longphase-to 跑完一個 tumor 樣本（例如 HCC1395 5kHz）的 tagged BAM 上，把每條 read 的 HP tag 分類後計數，得出：

HP tag 值含義占 tagged reads %
HP:i:1germline HP140.5%
HP:i:11somatic on HP13.5%
HP:i:2germline HP251.6%
HP:i:21somatic on HP24.1%
HP:i:33somatic ambiguous0.3%

注意 — 這張表是 paired mode（longphase-s）的數字，所以是接近平衡的。TO mode 跑出來的對應比例會非常極端：HP1 系列（1+11）佔 ~94.6%，HP2 系列（2+21）只佔 ~5.4% — 算出來就是 17.3:1。

要解釋為什麼這個數字會是 17.3 而不是 1 或 50，要看 code 怎麼決定每一條 read 的 tag。

2.用「面試官」比喻看清 getVote() 的 bug

想像每條 read 走進一間面試室，房間裡有三組面試官輪流問問題：

順序面試官問什麼
第 1 個面試官 A「你身上有 somatic 證據嗎？」(HP1_1 vs HP2_1)
第 2 個面試官 B「你身上有 HP3 或 somatic 證據嗎？」
第 3 個面試官 C「你身上有 germline 證據嗎？」(HP1 vs HP2)

正常邏輯應該是三組都問完，看誰票多誰勝。但 baseline code 寫的是：

只要前一個面試官看到任何東西（≥1 票），立刻決定結果，後面的面試官根本不會被問到。

對應原始碼是 getVote() 裡的這段（baseline HaplotagProcess.cpp:506-530）：

std::vector<std::pair<int, int>> variantKeys = {
    {HAPLOTYPE1_1, HAPLOTYPE2_1},   // ← pair[0]: somatic 排第一 ❌
    {HAPLOTYPE3,   HAPLOTYPE2_1},   // ← pair[1]:
    {HAPLOTYPE1,   HAPLOTYPE2}      // ← pair[2]: germline 排最後 ❌
};
for (const auto& pair : variantKeys) {
    if (countMap[key1] > 0 || countMap[key2] > 0) {   // 看到任一票就進
        ...
        break;   // ← 致命：跳出迴圈，後面再也不檢查 ❌
    }
}

具體個案：5 票 HP2 + 1 票 HP1 somatic 怎麼變成 HP:i:11

假設一條 read 跨過 5 個 germline het 位點 + 1 個 somatic SNV，countMap 累積完是：

countMap = [0, 5, 0, 1, 0]
            HP1=0  HP2=5  HP3=0  HP1_1=1  HP2_1=0

正常推論：5 票 germline 強烈指 HP2 → 應該標 HP:i:2 或 HP:i:21。但 baseline 跑出：

迴圈檢查 paircountMap 值結果
0(HP1_1=3, HP2_1=4)1, 0條件成立 → hpResult = 11 → break
1(HP3, HP2_1)—永遠不執行
2(HP1, HP2) germline—永遠不執行

→ 這條 read 被標 HP:i:11（HP1 系列），5 票 germline HP2 證據完全被無視。這就是 chr19 752 條 victim reads 的精準個案。

3.為什麼 somatic 那 1 票偏偏都指 HP1

第 2 節解釋了「為什麼 1 票會蓋過 5 票」，但還沒回答「為什麼是偏 HP1 而非偏 HP2」。這要看 VCF parser 怎麼把 GT 映射成 ref/altHaplotype（HaplotagProcess.cpp:161-194）：

else if (gtValue[0] == '0' && gtValue[2] == '0') {       // 0|0 ← somatic
    std::string gt2Value = formatSample.getValue("GT2");
    if (gt2Value == "1|.") altHaplotype = HAPLOTYPE1_1;     // somatic on HP1
    else if (gt2Value == ".|1") altHaplotype = HAPLOTYPE2_1; // somatic on HP2
    ...
}

parser 完全依賴 VCF 的 GT2 欄位決定 somatic 在哪一條 haplotype。而 GT2 是上游 phasing 階段寫進去的。所以 somatic 的方向偏移其實在 VCF 階段就已固化，bug 之所以放大它，是因為兩個額外條件：

Q1 Tumor sub-clone somatic 為何天生「方向一致」？ CORE

癌細胞是從同一個祖先細胞演化來的 — 同一批 somatic mutation 落在同一條 haplotype 上是必然的（同源 lineage）。如果 sub-clone A 在 HP1 帶 SNV-X，A 的所有後代細胞都會在 HP1 帶 X，read level 看到的 ALT 自然都指向 HP1。

→ tumor sample 的 somatic 票天生就偏一邊，這是生物學事實，不是 bug。

Q2 上游 phasing 為什麼還會放大這個偏移？ CORE

longphase-to TO mode 在建 phasing graph 時，把 somatic SNV 也當投票員（即「球員兼裁判」）。一旦 somatic 一致偏向 HP1，phasing graph 就被拉向那一邊：

  • 建 graph 時 somatic edge weight 暴漲
  • edge weight 暴漲 → 自我強化
  • 寫進 VCF 的 GT2 大多變成 1|.（HP1 方向）

→ parser 拿到後，把絕大多數 somatic 寫成 altHaplotype = HAPLOTYPE1_1。somatic 票方向在進 countMap 之前就已固化偏 HP1。

4.兩個放大器把 1:1 變成 17:1

到這裡可以拆解出 bug 從「mechanism」到「實測 17.3:1」的兩個放大器：

放大器機制來源貢獻
A somatic 票方向一致（≈95% 指 HP1） tumor 同源 lineage + 上游 phasing 球員兼裁判 提供「偏移方向」
B 1 票就 break，germline 證據完全失效 getVote() pair 排序 + break early 提供「規模放大」

把 A × B 疊起來：

P(read 受影響) × P(方向偏 HP1 | 受影響) × 平均放大係數
   = 高           × 接近 1（A 提供）        × 大（germline 完全無視）
   ≈ 17.3 : 1

算術驗證：17.3 / (17.3 + 1) = 17.3 / 18.3 ≈ 0.946 = 94.6% 偏 HP1，與整合報告 §2.1 全基因組統計一致。

5.V6 怎麼修：讓 germline 永遠先發言

V6 把整個面試流程改寫成兩層明確結構，不再用「pair 排序 + break」這種隱式邏輯。對應原始碼 longphase-to-mod/HaplotagProcess.cpp:512-559：

// V6 explicit two-layer
int germlineHP1 = countMap[HAPLOTYPE1];
int germlineHP2 = countMap[HAPLOTYPE2];
int somaticTotal = countMap[HAPLOTYPE1_1] + countMap[HAPLOTYPE2_1] + countMap[HAPLOTYPE3];

// Layer 1: germline 永遠先決定方向
int germlineResult = 0;
if (germlineHP1 > 0 || germlineHP2 > 0) {
    if (germlineHP1 >= germlineHP2) germlineResult = 1;      // 指 HP1
    else                            germlineResult = 2;      // 指 HP2
}

// Layer 2: somatic 只負責 annotate（不改方向）
if (somaticTotal > 0) {
    if (germlineResult == 1)      hpResult = 11;   // HP:i:11
    else if (germlineResult == 2) hpResult = 21;   // HP:i:21
    else                          hpResult = 33;   // HP:i:33 (germline 為 0 時保守)
} else {
    hpResult = germlineResult;
}

對前面同一個 countMap = [0, 5, 0, 1, 0] 跑 V6：

階段邏輯結果
Layer 1 (germline)germlineHP1=0 < germlineHP2=5 → germlineResult = 2方向確定為 HP2 ✓
Layer 2 (somatic 疊加)somaticTotal=1 > 0 && germlineResult == 2 → hpResult = 21HP:i:21 ✓

同樣的 read，baseline 標成 HP:i:11（錯，1 票翻盤 5 票），V6 標成 HP:i:21（對，方向跟 germline 走，尾巴加 1 表示有 somatic）。

V6 強制兩個不變式：(1) 沒有 break、germline 永遠被讀；(2) somatic 不能決定方向（germline 為 0 時保守標 33，不從 somatic 推方向）。
修正率：chr19 752 / 752 victims = 100%；全基因組 34,855 / 34,855 = 100%；無任何反向案例。

6.Paired mode 為什麼沒有同 bug

最容易誤解的點 — paired mode 並非用了一樣的 longphase-to 修對，而是從頭就用完全不同的 binary：

項目TO modePaired mode
Binarylongphase-tolongphase-s somatic_haplotag
Codebase repo/big8_disk/.../longphase-to//big8_disk/.../longphase-s/ (獨立 fork)
HP tag 編碼HP:i: 整數 (1/2/11/21/33)HP:Z: 字串 (1/2/1-1/2-1/3)
tag 邏輯來源HaplotagProcess.cpp:506SomaticHaplotagProcess.cpp:533
HP1:HP2 整體比17.3 : 1 (priority bug)
HP1:HP2 整體比1 : 1.275 (近 1:1，無 bug)

Paired mode 同位點 HP1-1 / HP2-1 共現是真實 sub-clone signal（som_ratio 在 chr19 跨 1 Mb windows 從 0 到 1 全範圍分佈），不是 artifact。

7.一句話收尾 + 流程對照

17.3:1 = 「somatic 票天生偏一邊」 × 「getVote() 看到 1 票就 break、germline 完全被無視」。Bug 不在創造方向，而是把上游已有的微小偏向放大成 17 倍。V6 把 germline 改成永遠先決定方向，就修對了。

baseline 的 getVote 流程

read 進來 → 算 countMap → [問 somatic? 有票就決定 + break] → 寫 HP tag ↑ germline 永遠沒輪到 ❌

V6 的 getVote 流程

read 進來 → 算 countMap → [先問 germline → 決定方向 1 / 2] → [再問 somatic → 決定要不要加 "1" → 11 / 21 / 33] → 寫 HP tag ✓

差別只在「誰先問」「能不能 break」這兩個邏輯選擇，但對 BAM 統計值的影響是 17 倍 vs 1 倍 的差距。
