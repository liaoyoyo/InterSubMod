# 專案架構、內容與資料結構審查與整理決策清單

- 日期：2026-02-28
- 範圍：`/big8_disk/liaoyoyo2001/InterSubMod` 全專案（程式碼、腳本、文件、資料與輸出結構）
- 目的：找出可優化之處，並整理出需要你決策的方案
- 原則：本文件僅審查與提案，不進行破壞性重整

## 1. 實際現況摘要（量化盤點）

### 1.1 目錄與容量

| 路徑 | 大小 | 備註 |
|---|---:|---|
| `output/` | 8.1G | 579,448 檔案，為最大體積來源 |
| `build/` | 360M | 建置產物 |
| `analysis/` | 9.4M | 根層分析專區（非 docs） |
| `docs/` | 4.5M | 239 檔案（含 207 個 `.md`） |

### 1.2 程式架構

- `src/`（27 檔）與 `include/`（31 檔）模組對位整齊：`core/io/utils`
- 測試分為兩層：
  - `tests/`（GoogleTest unit tests）
  - `src/test/`（phase 驗證可執行檔）
- `CMakeLists.txt` 結構清楚，但依賴為線上抓取（jemalloc、eigen、googletest），在離線/隔離環境重現性較差

### 1.3 腳本現況

- `scripts/` 實際有 25 檔，但 Git 追蹤僅 8 檔
- 未追蹤但重要的腳本群：
  - `scripts/analysis/*`
  - `scripts/pipeline/*`
  - `scripts/hooks/*`

### 1.4 文件現況

- `docs` 子目錄分布（部分）：`archive(86)`, `experiments(34)`, `plans(24)`, `analysis(9)`
- 命名規範一致性（依 `docs/README.md` 的「YYYYMMDD_主題_流水號」）偏低
- 文件 metadata 區塊合規率偏低：207 份 md 中僅 23 份含 `<!-- ... -->` 開頭 metadata
- 本地 Markdown 連結失效：46 筆（含相對路徑、file://、舊檔名）

### 1.5 根層雜項檔案

根層目前存在不屬於核心入口的文件：
- `baseline_metrics.txt`
- `baseline_output.log`
- `findings.md`
- `progress.md`
- `task_plan.md`

建議下沉至 `docs/` 對應目錄，降低 repo 根層噪音。

## 2. 主要問題與可改善點

## 2.1 文件與實作不一致（高優先）

1. `README.md` / `QUICKSTART.md` / `README_PROJECT_SUMMARY.md` 仍引用 `scripts/run_vcf_all_snv.sh`，但目前主要腳本為 `scripts/run_vcf_all_snv.sh`。
2. 多份文件仍描述舊輸出結構（`region_*`）與舊流程命名，與現有 `output/20260118_*` 結構不一致。

## 2.2 文件命名與分類策略混用（高優先）

1. 同類文件散落在 `docs/analysis`、`docs/experiments`、`docs/reports` 與根層 `analysis/`。
2. 部分目錄採年月分層（例如 `plans/2026/01`），部分採主題分層（例如 `plans/methylation_significance`），規則並存但未定義優先權。

## 2.3 Git 追蹤邊界不清（高優先）

1. 實際會用到的 pipeline/analysis 腳本尚未納入追蹤，形成「本地可跑、團隊不可重現」風險。
2. `.gitignore` 使用 `*output*/` 與 `analysis/*` 這類廣泛規則，容易造成「新結果/新腳本被忽略」的誤判。

## 2.4 測試資料治理不足（中優先）

1. `tests/test_bam_reader.cpp` 依賴 `data/bam/test.bam`，目前缺失導致長期 skip。
2. `data/README.md` 描述之結構與實際 `data/` 內容不一致（目前僅最小測試資料）。

## 2.5 完成度與狀態管理不足（中優先）

使用者想要的「完成度分資料夾」目前未被正式制度化；現況多以檔名/內容描述狀態，缺少機器可讀的狀態層。

## 3. 建議目標結構（不破壞現有程式）

## 3.1 程式與執行層（維持）

- 保留：`src/`, `include/`, `tests/`, `scripts/`, `tools/`
- 補強：
  1. `scripts/` 完整追蹤
  2. `scripts/README.md`（入口腳本、參數、依賴）

## 3.2 文件層（強化）

建議新增並固定以下結構：

```text
docs/
├── standards/                  # 規範：命名、模板、benchmark 口徑
├── plans/YYYY/MM/
├── reports/YYYY/MM/
├── experiments/
│   ├── in_progress/YYYY/MM/    # 進行中（草稿）
│   ├── validated/YYYY/MM/      # 已驗證（可引用）
│   └── finalized/YYYY/MM/      # 最終結論（對外口徑）
├── decisions/YYYY/MM/          # 需人決策的 ADR/Decision Log
└── archive/
```

## 3.3 資料與輸出層（建議）

- 將大規模執行輸出根目錄改為 repo 外（例如 `/big8_disk/.../InterSubMod_runs/`）
- repo 內 `output/` 只保留：
  1. 小型範例
  2. 報告引用索引
  3. 最新一次基準 run 的摘要

## 4. 命名與文件規範（建議版）

## 4.1 檔名規範

1. 預設採：`YYYYMMDD_主題_流水號.md`
2. 例外僅限：`README.md`, `CURRENT_FOCUS.md`, `INDEX.md`, 架構長期文件（`snake_case.md`）
3. 禁止：空格、混用日期格式（如 `2026-02-13_...`）

## 4.2 文件 metadata 規範

每份新文件強制包含：
- 建立時間
- 狀態（draft / validated / finalized / archived）
- 資料來源
- 驗證命令
- 關聯文件

## 4.3 連結規範

1. 禁止 `file://` 連結
2. 相對路徑連結必須在 repo 內可解析
3. 每次重整後跑一次 link check

## 5. 整理與重整的三種方案（你需要決策）

## 方案 A：低風險快修（1-2 天）

- 只做高衝擊修正：
  1. 修正 README/QUICKSTART 腳本名稱
  2. 補 `scripts/README.md`
  3. 修掉主要失效連結（前 20 筆）
  4. 建立 `docs/standards/` 與模板
- 優點：快、風險低
- 缺點：歷史文件仍混雜

## 方案 B：平衡重整（推薦，3-5 天）

- 包含方案 A，外加：
  1. 建立 `experiments/in_progress|validated|finalized`
  2. 將根層雜項文件下沉到 `docs/reports`/`docs/archive`
  3. 將關鍵未追蹤腳本納入版本控管
  4. 統一 2026 年文件命名
- 優點：顯著提升可維護性與可重現性
- 缺點：會有一批檔案移動與重命名

## 方案 C：全面重構（1-2 週）

- 全量修正歷史文件命名、連結、metadata；統一所有目錄策略
- 優點：最乾淨
- 缺點：成本最高、風險最高、可能打斷目前研究節奏
