Engineering Root Cause Analysis

HP tag 17.3 : 1 偏移 — 根本原因解釋（工程師敘述版）

為何 longphase-to TO mode 輸出 BAM 的 HP1 系列 ：HP2 系列 reads 比會等於 17.3 ：1？ 本文以 C++ 原始碼級因果鏈，回答「機制×生物 兩條因素疊乘的湧現實測值」這句結論的具體含意。

日期 2026-05-14 狀態 validated 受眾 engineer-peers / PI 閱讀時間 約 12 分鐘 關聯 完整工程報告（13 段） · 3 分鐘 brief

TL;DR — 一句話結論

17.3 ：1 不是 code 裡寫死的常數，也不是樣本生物特性，而是 「algorithm flaw（兩個小設計選擇）」× 「biology + 上游 phasing 把 somatic 票方向偏掉」 兩條因素疊乘後的湧現實測值。

Algorithm flaw 在 HaplotagProcess.cpp:506-530 的 getVote() 函式內： variantKeys vector 把 somatic pair 排第一 + 看到 ≥1 票就 break 跳出迴圈 → germline 票永遠不被檢查。

生物因素：tumor sub-clone 為同源 lineage，somatic 必落同一條 haplotype； 上游 phasing 把 somatic 也當投票員建 graph（球員兼裁判）， 使 VCF 寫出的 GT2 約 95% 偏 1|. 方向（HP1）。

兩條因素疊乘後，17.3 / (17.3 + 1) ≈ 94.6% reads 被誤推 HP1， 與全基因組 94.6% somatic ALT 偏 HP1 的實測值一致。

§2Bug 位置 — HaplotagProcess.cpp:506-530 的 getVote()

函式在整個 pipeline 中的角色

longphase-to 對 tumor BAM 做 haplotagging — 每條 read 寫入 HP:i: 整數 auxiliary tag，標示這條 read 來自哪條 haplotype。實際決策點如下：

countMap 是什麼

countMap 為 std::array<int, 5>，5 個 slot 對應 5 種 haplotype 票數 （定義在 Util.h:19-26）：

Slotenum 名BAM 編碼語意
0HAPLOTYPE1HP:i:1germline HP1
1HAPLOTYPE2HP:i:2germline HP2
2HAPLOTYPE3HP:i:33somatic ambiguous（兩 sub-clone 都帶）
3HAPLOTYPE1_1HP:i:11somatic on HP1 background
4HAPLOTYPE2_1HP:i:21somatic on HP2 background

getVote() 的工作就是：拿到 5 個 slot 的票數，決定該 read 的 hpResult （最終寫進 BAM 的 HP:i 整數）。Bug 就在這個決策邏輯內。

§3第一條因素 — 兩個 algorithm flaw（缺一不可）

Baseline 的 getVote() 邏輯（精簡呈現）：

BASELINE · longphase-to/HaplotagProcess.cpp:506-530

void HaplotagProcess::getVote(std::array<int, HAPLOTYPE_SIZE> &countMap,
                              double &min, double &max, int &hpResult) {
    std::map<int, int> haplotypeBase = {
        {HAPLOTYPE1, 1}, {HAPLOTYPE2, 2},
        {HAPLOTYPE1_1, 11}, {HAPLOTYPE2_1, 21},
        {HAPLOTYPE3, 33}
    };
    std::vector<std::pair<int, int>> variantKeys = {
        {HAPLOTYPE1_1, HAPLOTYPE2_1},   // ← pair[0]: somatic  ← 排第一
        {HAPLOTYPE3,   HAPLOTYPE2_1},   // ← pair[1]
        {HAPLOTYPE1,   HAPLOTYPE2}      // ← pair[2]: germline ← 排最後
    };
    for (const auto& pair : variantKeys) {
        int key1 = pair.first;
        int key2 = pair.second;
        if (countMap[key1] > 0 || countMap[key2] > 0) {
            if (countMap[key1] > countMap[key2]) {
                min = countMap[key2]; max = countMap[key1];
                hpResult = haplotypeBase[key1];
            } else {
                min = countMap[key1]; max = countMap[key2];
                hpResult = haplotypeBase[key2];
            }
            break;                                    // ← 致命跳出
        }
    }
}

Flaw A — variantKeys 把 somatic 排第一

variantKeys[0] = (HAPLOTYPE1_1, HAPLOTYPE2_1) 排在前面， variantKeys[2] = (HAPLOTYPE1, HAPLOTYPE2)（germline）排在最後。 這個順序本身不是 bug — 但搭配 Flaw B 就會放炸藥。

Flaw B — 看到第一個非零 pair 即 break 跳出

觸發條件 countMap[key1] > 0 || countMap[key2] > 0 只需要 1 票就會 fire。一旦 pair[0]（somatic）命中，迴圈 break 跳出， 後面 pair[2]（germline）根本不會被檢查。

兩個 flaw 疊乘的個案 trace

假設一條 read 跨越 5 個 germline het（全部投給 HP2，countMap[1] = 5）+ 1 個 somatic（HP1 方向，countMap[3] = 1）：

Baseline 結果：pair[0] 觸發（countMap[3] = 1 > 0）， hpResult = haplotypeBase[3] = 11，break。 5 票 germline HP2 證據被完全無視。BAM 寫入 HP:i:11。

正確結果：germline 5 票 HP2 應決定方向（HP2），somatic 1 票決定 annotation → 寫入 HP:i:21（somatic on HP2 background）。

為何單獨任一條都不夠

若只有 Flaw A 而沒有 Flaw B：迴圈會跑完 3 個 pair，會比較 pair 間的票數， germline 的 5 票仍會勝出 → 不會誤標。

若只有 Flaw B 而沒有 Flaw A（germline 排第一）：第一個非零 pair 通常是 germline， germline 1 票就會決定方向，somatic 後續再疊加。

必須「somatic 排第一」+「1 票觸發 break」兩者同時成立， 才會發生 systematic 偏移。

§4第二條因素 — Somatic 票為何系統性偏 HP1（生物 + 上游 phasing）

僅有 algorithm flaw 還不夠 — 若 somatic 票在 HP1 / HP2 兩邊均等分佈， bug 仍會 break early 但偏向是隨機的，BAM 統計會接近 1 : 1。 系統性偏向 HP1 來自兩個獨立的「上游給定」：

Enabler 1 — Tumor sub-clone 同源 lineage（純生物）

  • tumor sub-clone 是 single ancestor cell 的後代，所有 somatic mutations 在 lineage 內必落在同一條 haplotype。
  • 對單一 sub-clone 內所有 reads 而言，countMap[HAPLOTYPE1_1] 與 countMap[HAPLOTYPE2_1] 中只會有一邊被持續累加。
  • 到底偏哪一邊（HP1 或 HP2）由 lineage 起源決定 — 但對整個 BAM 而言一致偏一邊。

Enabler 2 — 上游 phasing「球員兼裁判」放大偏向

longphase phasing layer 在建 phasing graph 時把 somatic variant 也當投票員， 讓 somatic edge weight 計入連通性 → 同 lineage 的 somatic 互相 reinforce → 自我強化偏向。具體下游影響：

  • VCF 寫出的 GT2 欄位（phased genotype）HCC1395 約 95% 偏 1|. 方向。
  • baseline HaplotagProcess.cpp:172, 185 的 VCF parser 依 GT2 直接寫 altHaplotype = HAPLOTYPE1_1（slot 3）。
  • → 進入 getVote() 前，countMap[3] 系統性 ≥ countMap[4]。
這條因素的關鍵特徵

Enabler 2 不是 bug — phasing graph 把 somatic 當投票員是 longphase 原本的設計選擇（提高低 het density 區的 phasing recall）。 問題是 tagging layer（getVote()）沒有預期 somatic 票會被上游放大， 仍然信任「somatic 票方向 = 真實 haplotype 方向」。

換言之，Enabler 2 是 contract assumption mismatch： 上游放大 somatic edge → 下游沒有對應的去偏校正。

§5疊乘量化 — 為何放大到 17.3 倍

從 read 級到 BAM 級的放大鏈：

算術一致性檢核

  • BAM 統計層級：HP1 系列 / HP2 系列 = 17.3 / 1 → HP1 比例 = 17.3 / (17.3 + 1) = 94.5%
  • 整合報告 §2.1 全基因組量測：somatic ALT 偏 HP1 = 94.6%
  • chr19 SP1 個案：HP1 ：HP2 = 113 ：0（極端但同方向）

三個層級數字吻合，符合「機制 × biology 疊乘的湧現實測值」的描述。

染色體分佈一致性（排除 region-specific 解釋）

若 17.3:1 來自特定 region（如 chr8 LOH hotspot），則 priority bug victims 應集中該區。 實際分佈：

  • chr19 占全基因組 victims：752 / 34,855 = 2.16%（rank 19，與 chr19 在 genome 占比相當）
  • chr8 enrichment：0.34× genome avg（bug 冷區，與 chr8 LOH+HPSig FP hotspot 7.4× 是不同 layer）

→ bug 在所有 chromosome 一致發生，屬於 systematic algorithm flaw，不是 region-level artifact。

§6對照組 — 為何 Paired mode 不受影響

若 17.3:1 是樣本本身的 LOH 不對稱性，那麼同一份 HCC1395 BAM 在 paired mode 跑出來應該一樣偏。 實測結果：

為何同一份樣本兩個 binary 結果差這麼大

longphase-to 與 longphase-s 是獨立的 fork， tagging layer 完全是兩份 C++ 實作。兩者共享 longphase 上游 phasing 的部分模組， 但 bug 不在共享部分 — bug 在 TO fork 自己的 HaplotagProcess.cpp 內。

這個對照同時提供另一層證據： 若 bug 在共享的 phasing layer（例如 Enabler 2 的球員兼裁判），那兩個 binary 都會偏； 但 paired mode 不偏（1:1.275）→ 證實 bug 的致命環節在 tagging layer， Enabler 2 只是提供方向偏好而非單獨致命。

§7修補方向 — V6 patch（two-layer 結構）

V6 把 getVote() 改寫為 explicit two-layer： Layer 1 germline 決定方向（HP1 / HP2）， Layer 2 somatic 疊加 annotation（11 / 21 / 33）。 germline 為 0 時保守標 HP:i:33，不嘗試用 somatic 推方向。

V6 · longphase-to-mod/HaplotagProcess.cpp:512-559

void HaplotagProcess::getVote(std::array<int, HAPLOTYPE_SIZE> &countMap,
                              double &min, double &max, int &hpResult) {
    // V6 two-layer:
    //   Layer 1: Germline evidence (HP1 vs HP2) — highest priority
    //   Layer 2: Somatic annotation — determines final HP tag encoding

    int germlineHP1 = countMap[HAPLOTYPE1];
    int germlineHP2 = countMap[HAPLOTYPE2];
    int somaticHP1  = countMap[HAPLOTYPE1_1];
    int somaticHP2  = countMap[HAPLOTYPE2_1];
    int somaticTotal = somaticHP1 + somaticHP2 + countMap[HAPLOTYPE3];

    // Layer 1: Germline decides direction
    int germlineResult = 0;
    if (germlineHP1 > 0 || germlineHP2 > 0) {
        if (germlineHP1 >= germlineHP2) {
            min = germlineHP2; max = germlineHP1;
            germlineResult = 1;
        } else {
            min = germlineHP1; max = germlineHP2;
            germlineResult = 2;
        }
    } else {
        min = 0; max = 0;
    }

    // Layer 2: Combine germline + somatic annotation
    if (somaticTotal > 0) {
        if (germlineResult == 1)      hpResult = 11;
        else if (germlineResult == 2) hpResult = 21;
        else                          hpResult = 33;   // germline absent → conservative
    } else {
        hpResult = germlineResult;   // 0, 1, or 2
    }
}

V6 強制的三條 invariants

  1. Never short-circuit germline：無 break，germline slot 永遠被讀取。
  2. Somatic 不選方向：除非 germline 為 0，否則 somatic 只決定 11/21/33 的後綴。
  3. Germline-absent 保守 fallback：germline = 0 且 somatic > 0 時退標 HP:i:33， 不再嘗試從 somatic 票推方向（避免繼承 priority bug）。
V6 vs V5 trade-off（為何不用 Layer 1.5）

V5 曾嘗試在 V3F two-layer 基礎上加 Layer 1.5：germline = 0 時用 somatic votes 推方向（恢復 marker coverage）。 但 paired cross-ref audit 發現 V5 在 germline-absent 區（如 cnLOH / amplicon） 與 baseline 4.19:1 偏 HP1 完全相同 — Layer 1.5 繼承了同一個 priority bug。

V6 移除 Layer 1.5，germline-absent 區保守標 33。代價是 hp=33 rate 增加； 好處是全域 HP1 ：HP2 ratio 接近中性，跨樣本 4/4 驗證 ratio ∈ [0.611, 1.243]。

API 影響：零

函式 signature 完全不變： 

void getVote(std::array<int, HAPLOTYPE_SIZE> &countMap,
             double &min, double &max, int &hpResult);

外部 caller（judgeHaplotype() 內呼叫處）無需任何改動， binary 重新編譯即可替換。Caller F1 vs SEQC2 truth：HCC1395 0.93 / 0.6 purity 四版（baseline / V3F / V5 / V6）皆為 0.7166 / 0.6273， 證實 V6 patch 不影響上游變異檢出（不改 caller，只改 tagging）。

口徑說明：上述 F1 為本專案 caller-level F1；longphase 原論文 §4.3 F1 採用 V_H / V_L post-filter 不同 metric 口徑， 詳見 InterSubMod/.claude/CLAUDE.md 外部工具 claim 查詢規則（先查 KB 後對照）。
