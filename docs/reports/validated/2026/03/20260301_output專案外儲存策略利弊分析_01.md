# output 放在專案外的利弊分析

## 1. 結論

`output` 實體放在專案外（另一顆硬碟），repo 內保留 `output/` 軟連結入口，是目前最適合 InterSubMod 的策略。  
理由：兼顧 I/O 空間、版本控管潔淨、與 Agent 路徑穩定性。

## 2. 好處（Pros）

1. **避免污染 Git 工作樹**  
   大量結果檔不會混入 repo 追蹤，減少誤提交風險。
2. **更好的儲存彈性**  
   可使用較大容量磁碟承載長期實驗輸出，避免 repo 所在磁碟爆滿。
3. **保留固定入口**  
   `output/` 作為穩定路徑，不影響既有腳本與 Agent 的路徑習慣。
4. **便於跨批次累積**  
   外部儲存可獨立保留歷史 runs，不需隨 repo 清理週期而刪除。

## 3. 風險（Cons）

1. **軟連結失效風險**  
   掛載異常或目標路徑變動時，流程會在執行期才報錯。
2. **可攜性下降**  
   換機器時若外部路徑不存在，腳本需重新設定。
3. **路徑語彙混亂**  
   若腳本同時混用 `output/` 與絕對外部路徑，Agent 容易誤判實際輸出位置。
4. **清理責任邊界不清**  
   若未定義刪除流程，容易發生誤刪或無法追溯誰清掉資料。

## 4. 風險控制建議

1. `output/` 一律保留為唯一入口語彙，避免新文件再寫硬編碼舊路徑。
2. 異常時才執行 `check_ai_agent_readiness.sh`，確認：
   - symlink 目標
   - docs 結構
   - MCP 連線設定
3. 刪除政策採「先搬移後人工刪除」：
   - 先搬移至 `/big8_disk/liaoyoyo2001/InterSubMod_runs/Archive_pending_delete/`
   - 由使用者手動最終刪除
4. 需清理時，僅允許在可審核的執行腳本中實作，不在互動任務中直接清空。

## 5. 適用判斷

以下情境特別適合專案外輸出：
1. 單次 run 產出大量中間檔與圖檔。
2. 需要保留多版本實驗結果做對照。
3. repo 主要作為程式碼與文件治理，不作為資料湖。

以下情境可考慮改回 repo 內輸出（不建議目前採用）：
1. 小型教學專案，輸出規模極小。
2. 完全單機、短期任務且不需歷史追溯。
