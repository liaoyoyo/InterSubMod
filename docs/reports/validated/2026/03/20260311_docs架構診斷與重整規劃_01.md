# docs 架構診斷與重整規劃

## 重點結論

目前 `docs/` 的核心問題不是「完全沒有分類」，而是「分類已經存在，但經過多輪擴充後，**正式文件、研究工作區、簡報產物、QA 資產、AI 對話 provenance、歷史骨架** 同時可見且彼此交錯」，導致入口雖多，語意卻不夠穩定。最主要的混亂來源有 5 類：`類別語意重疊`、`非 Markdown 產物混入 canonical docs`、`半完成/空骨架長期可見`、`研究工作區與正式文件混放`、`歷史 provenance 與可引用結論沒有明確區隔`。最合理的整理方式不是一次大搬家，而是分成三輪：先修正低風險入口與明顯錯位，再處理研究工作區與參考文件的語意邊界，最後才整理歷史 provenance 與長尾骨架；每一輪都必須先產生 mapping/manifest，再搬移、驗證、更新索引，避免把現在可用的導航系統打壞。

### 1.2 判讀原則

本報告中的「混亂」不是單指目錄多，而是指以下情況：

1. 同一種內容可以合理落在 2 個以上類別，使用者無法快速判定唯一入口。
2. 目錄名稱看起來像正式文件類別，但實際內容是中介產物、腳本、圖檔或 QA 資產。
3. 某些目錄是歷史骨架或保留欄位，但長期暴露在主導航裡，增加查找成本。
4. 一份資料同時扮演「研究工作區」與「正式文件庫」，造成治理規則不一致。

## 3. 為什麼現在會覺得混亂

### 3.1 類別語意重疊

這是最核心的原因。

#### 例 1：`analysis/` vs `reports/validated/` vs `research/`

本次 round 1 已將原本位於 `docs/analysis/2026/03/20260302_subsample_methylation_confounding_analysis_01.md` 的文件收斂到：

[docs/reports/validated/2026/03/20260302_subsample_methylation_confounding_analysis_01.md](/big8_disk/liaoyoyo2001/InterSubMod/docs/reports/validated/2026/03/20260302_subsample_methylation_confounding_analysis_01.md)

這份文件的實際內容是一份完整分析報告，語意上更像：

1. `docs/reports/validated/...` 的分析報告，或
2. `docs/research/...` 的主題研究文檔

它放在 `analysis/` 會造成疑問：
- `analysis` 是正式類別嗎？
- 之後所有分析都要放這裡嗎？
- 那 `reports/validated` 又是什麼？

#### 例 2：`references/manual/` vs `references/2026/`

`docs/references/manual/` 已形成穩定語意：手冊、agent 規格、操作說明。  
本次 round 1 已將原本位於 `docs/references/2026/...` 的外部參考收斂到 `docs/references/external/...`。例如：

[docs/references/external/2026/03/20260302_tissue_origin_methylation_confounding_literature_review_01.md](/big8_disk/liaoyoyo2001/InterSubMod/docs/references/external/2026/03/20260302_tissue_origin_methylation_confounding_literature_review_01.md)

它其實是文獻回顧，不是操作手冊。

這代表 `references/` 目前至少混了兩種東西：

1. 手冊/使用規範
2. 外部文獻/參考整理

若不拆清楚，後續只會繼續長歪。

### 3.2 正式文件與簡報產物混放

`docs/presentations/` 已經是一個成熟且合理的獨立類別；本次 round 1 已將原先落在 `reports/validated` 的簡報移出，例如：

- [docs/presentations/validated/2026/03/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01.pptx](/big8_disk/liaoyoyo2001/InterSubMod/docs/presentations/validated/2026/03/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01.pptx)

這會形成雙入口：

1. `docs/reports/...` 看得到週報 `.md`
2. `docs/presentations/...` 又有簡報版本
3. `reports/.../assets` 還有 QA 圖片與盤點 TSV

結果是：同一份成果的「報告」、「簡報」、「QA 資產」、「版本檔」散在多層。

### 3.3 研究工作區與正式 docs 混在一起

[docs/research/methylation_f1_optimization/README.md](/big8_disk/liaoyoyo2001/InterSubMod/docs/research/methylation_f1_optimization/README.md) 對應的目錄不是純文件，而是整個研究工作區，內含：

- `04_scripts/*.py`
- `05_results/**/*.png`
- 各 phase report `.md`

這種結構在短期研究很方便，但放在 `docs/` 會有兩個問題：

1. `docs/` 不再只是文件庫，而變成半個工作目錄。
2. 後續無法回答「這裡到底存的是 canonical docs，還是研究中間產物？」

### 3.4 provenance 與可引用結論沒有分層

`docs/provenance/ai_sessions/` 這類檔案很有價值，因為它記錄了「這次對話做了什麼」。但它和 `reports/validated` 的差別必須非常清楚：

- `reports/validated` 是可以拿來引用與複查的結論文件
- `ai_sessions` 是 provenance / session log

如果兩者都放在主導航層且命名相似，讀者會不知道哪一份才是 canonical。這在 AI 協作密集的專案中特別容易越來越亂。

### 3.5 空骨架與過渡目錄沒有被收斂

像 `data_specs/`、`reports/2026/02`、`references/api` 這種目錄目前沒有內容，但因為仍存在於主樹，等於一直暗示「這裡是正式類別」。

對治理來說，這會產生兩種負面效果：

1. 新文件容易被誤放進預留但尚未成熟的類別。
2. 讀者會把「空骨架」當成「查找成本」。

## 4. 目標狀態：什麼樣的 docs 會更清楚

### 4.1 目標原則

理想狀態不是目錄越少越好，而是每個類別都要回答下面三件事：

1. 這裡放的是什麼類型的知識？
2. 這裡的文件是否可以被正式引用？
3. 這裡是否允許非 Markdown 產物？若允許，附屬規則是什麼？

### 4.2 建議目標架構

```text
/docs
├─ README.md
├─ CURRENT_FOCUS.md
├─ standards/
├─ architecture/
├─ plans/YYYY/MM/
├─ experiments/{in_progress|validated|finalized}/YYYY/MM/
├─ reports/{validated|finalized}/YYYY/MM/
├─ presentations/{draft|validated|finalized}/YYYY/MM/
├─ research/{topic}/YYYY/MM/
├─ references/
│  ├─ manual/
│  └─ external/
├─ solutions/{topic}/YYYY/MM/
├─ provenance/
│  └─ ai_sessions/YYYY/MM/
└─ archive/
   ├─ YYYY/MM/
   └─ deep/
```

### 4.3 各類別的更精確語意

| 類別 | 應該放什麼 | 不應該放什麼 |
|---|---|---|
| `reports/validated` | 已整理好的分析報告、診斷報告 | `.pptx`、隨機 QA 圖、程式腳本 |
| `presentations/` | `.pptx`、`.pdf`、版本檔、該 deck 的 asset/QA | 週報正文 `.md` |
| `research/` | 主題研究文檔、長期研究脈絡 | 腳本、圖檔堆、實驗中間產物 |
| `references/manual` | 操作手冊、agent/skill 規格、使用說明 | 文獻綜述 |
| `references/external` | 文獻回顧、外部資料摘要 | 專案內流程手冊 |
| `provenance/ai_sessions` | AI 對話紀錄、工作 provenance | 正式報告、最終結論 |
| `archive/` | 已退出主導航但保留歷史的檔案 | 活躍主線文件 |

## 5. 具體怎麼拆分與重排會更好

### 5.1 P0：低風險、應優先處理

這一輪不碰研究邏輯，只修「明顯錯位」與「入口重複」。

#### P0-1. 把 `reports/` 裡的簡報移出，只保留報告正文

最明顯的例子：

- [docs/presentations/validated/2026/03/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01.pptx](/big8_disk/liaoyoyo2001/InterSubMod/docs/presentations/validated/2026/03/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01/20260311_研究主線週報_20260305_20260311_phase2_annotation整合_01.pptx)

建議：

1. `reports/` 只放 `.md` 報告與必要 `assets/`
2. `.pptx/.pdf/.version.json` 只留在 `docs/presentations/`
3. 原報告中改用連結指向 `docs/presentations/...`

#### P0-2. 凍結或隱藏空骨架類別

下列目錄若尚未啟用，不應繼續暴露成主入口：

- `docs/data_specs/`
- `docs/references/api`
- `docs/references/requirements`
- `docs/reports/2026/02`
- `docs/architecture/modules`

建議做法：

1. 若 2 週內沒有明確使用計畫，搬到 `docs/archive/2026/03/...pending_review...`
2. 或保留但從主 README 導航移除

#### P0-3. 將 `analysis/` 明確收斂

`docs/analysis/` 目前只有 1 份文件，分類成本高於收益。建議：

1. 把現有分析文件移到 `docs/reports/validated/...` 或 `docs/research/...`
2. `analysis/` 類別本身退出主導航
3. 後續不再新增 `analysis/` 作為主類別

### 5.2 P1：中風險、需要一輪 mapping 與驗證

#### P1-1. 將 `references/2026/` 收斂為 `references/external/`

目前 `references/2026/` 語意不清，容易與 `manual/` 混淆。建議：

1. 新增 `docs/references/external/YYYY/MM/`
2. 將文獻回顧、外部整理、第三方資源盤點搬到這裡
3. `manual/` 保留給操作手冊與 agent/skill 規格

#### P1-2. 將 `ai_sessions/` 改名為 `provenance/ai_sessions/`

這一點對語意幫助很大。`ai_sessions/` 真正的價值是 provenance，不是主文件類別。建議：

1. 新增 `docs/provenance/ai_sessions/YYYY/MM/`
2. 舊 `docs/provenance/ai_sessions/` 先搬進 archive 或保留映射過渡期
3. 在 `docs/README.md` 明確標示：這些不是 canonical 報告

#### P1-3. 簡報資產集中治理

`docs/presentations/validated/2026/03/assets/` 已有合理雛形，建議制度化：

1. 每個 deck 一個 asset 子目錄
2. QA 圖、抽字輸出、版本檔全部屬於該 deck
3. 不再把簡報 QA 圖散放到 `reports/.../assets`

### 5.3 P2：高風險、需要多輪迭代

#### P2-1. 重整 `docs/research/methylation_f1_optimization/`

這個目錄目前像一個研究工作區，不像 docs-only 類別。建議最終狀態：

1. `docs/research/methylation_f1_optimization/YYYY/MM/*.md` 保留文檔
2. `scripts/analysis/legacy/` 或 `scripts/analysis/research_support/` 放 `.py`
3. `output/` 或 `docs/reports/.../assets` 放結果圖
4. `docs/research/.../README.md` 只保留索引與說明

這一塊不建議一次搬完，因為它最容易打斷歷史引用。

#### P2-2. `concepts/` 與 `decisions/` 的長期定位

目前這兩個類別太薄，但不是錯。建議先觀察，不急著合併。更合理的策略是：

1. 若之後 `concepts/` 持續只有少量草稿，可視情況併到 `research/` 或 `plans/`
2. 若 `decisions/` 未成長，可保留但弱化導航

## 6. 哪些東西應搬到封存，而不是硬改名或硬保留

### 6.1 建議封存的對象

#### A. 空骨架或過渡骨架

符合以下任一條件者，建議優先搬封存：

1. 目前為空，且沒有明確啟用時程
2. 曾為過渡結構，現在已有新結構取代
3. 保留在主導航只會增加歧義

候選例如：

- `docs/reports/2026/02`
- `docs/data_specs/*`
- `docs/references/api`
- `docs/references/requirements`
- `docs/architecture/modules`

#### B. 舊 provenance 與歷史 session 目錄

若某些 `ai_sessions/` 僅提供歷史追溯，而不是目前仍需頻繁進入的入口，建議逐步退出主導航，移到：

- `docs/provenance/ai_sessions/...`
- 或 `docs/archive/YYYY/MM/...`

#### C. 已被更好類別取代的散落產物

例如：

- `reports/validated/.../*.pptx`
- `reports/.../assets/` 中屬簡報 QA 而非報告證據的圖

### 6.2 不建議直接封存的對象

以下類別雖然不完美，但現在仍是高價值主入口，不應先動：

1. `docs/experiments/`
2. `docs/reports/validated|finalized/`
3. `docs/plans/`
4. `docs/standards/`
5. `docs/presentations/`
6. `docs/README.md`
7. `docs/CURRENT_FOCUS.md`
8. `docs/experiments/INDEX.md`

## 7. 需要多次迭代與驗證的規範細節

這一段是重整成功與否的關鍵。

### 7.1 重整不能直接搬，必須先做 mapping

每一輪搬移前都應先產出 `move_manifest`，至少包含：

| 欄位 | 意義 |
|---|---|
| `round_id` | 第幾輪重整 |
| `category` | P0/P1/P2 |
| `reason` | 為何搬移 |
| `old_path` | 原路徑 |
| `new_path` | 新路徑 |
| `status` | `planned / moved / verified / rolled_back` |
| `notes` | 例外說明 |

### 7.2 每輪都要做的驗證

每輪搬移後至少做 4 類驗證：

1. `結構驗證`
   - 目標路徑是否符合命名/狀態規範
2. `連結驗證`
   - Markdown 連結是否失效
3. `導航驗證`
   - `docs/README.md`
   - `docs/CURRENT_FOCUS.md`
   - `docs/experiments/INDEX.md`
   是否仍能導到正確入口
4. `語意驗證`
   - 搬完後是否更容易回答「這東西應該去哪裡找」

### 7.3 驗證基線要先固定

在真正開始 round 1 搬移前，應先記錄一次目前的驗證基線，避免把既有歷史噪音誤認成這輪造成的問題。以本次盤點時的 `python3 scripts/analysis/validate_docs_structure.py` 為例：

1. `Name issues = 0`
2. `Metadata issues = 3`
3. `Link issues = 13`

其中大部分 link issue 來自 `docs/archive/deep/` 的歷史快照與既有手冊中的示意占位連結，因此後續 round 驗證應至少拆成：

1. `active docs baseline`
2. `archive/deep known noise`
3. `newly introduced issues`

否則會出現「明明本輪沒破壞任何有效文件，但驗證器仍報錯」的假陽性情況。

### 7.4 建議的三輪迭代方式

#### Round 1：入口與錯位修正

目標：把最明顯的錯位修掉，但不改深層歷史。

包含：

1. `reports/` 內 `.pptx` 清出
2. `analysis/` 收斂
3. 空骨架退出導航
4. 補一份 `docs/docs_structure_status.md` 或等效報告

#### Round 2：語意層分流

目標：把最容易混淆的類別拆清楚。

包含：

1. `references/manual` vs `references/external`
2. `ai_sessions` → `provenance/ai_sessions`
3. `presentations` 資產治理固定化

#### Round 3：研究工作區重構

目標：把 `research/` 從「工作區」收斂回「文檔庫」。

包含：

1. `research/.../04_scripts` 退出 `docs/`
2. `research/.../05_results` 改成標準資產路徑
3. 清理剩餘空骨架
4. 更新 README 與索引

## 8. 現在不該做的事

為了避免越整理越亂，以下事情現在不建議做：

1. **不要一次把 `docs/` 全部大改名**
   - 風險太高，會打斷大量內部連結與既有引用。
2. **不要把所有類別壓平成只有 `reports/experiments/research` 三類**
   - 這會失去 provenance、簡報、手冊等高價值語意。
3. **不要先動 `archive/deep/`**
   - 它的價值就是歷史快照，不應回寫。
4. **不要先碰高價值主入口**
   - `CURRENT_FOCUS.md`、`INDEX.md`、`README.md` 應最後更新，不應一開始大改。
5. **不要在沒有 manifest 的情況下搬移**
   - 否則之後無法追查哪一輪改了什麼。

## 11. 最終判斷

`docs/` 現在的問題，不是缺少規範，而是**規範已開始成形，但在快速擴張過程中，仍保留了太多過渡入口與混合型工作區**。因此最合理的治理方向不是重新發明整套結構，而是：

1. 保留已成熟且有用的主幹：`experiments / reports / plans / presentations / standards`
2. 收斂語意重疊的類別：`analysis / references / ai_sessions`
3. 把工作區與產物層從 `docs/` 主導航中逐步退出
4. 所有重整都採 manifest + 多輪驗證，不一次硬搬

也就是說，這不是一次性清理問題，而是**文件資訊架構（information architecture）治理問題**。要解決它，最有效的方法是：先固定邊界，再分輪收斂，而不是一次追求「看起來很整齊」。
