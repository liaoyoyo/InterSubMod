# IGV 自動截圖操作手冊

## 一句結論

在 InterSubMod 的代理執行環境中，**最穩定且整體最高效率** 的 IGV 自動截圖方式是：

1. 先用 **slim template**
2. 再用 **per-locus runner**
3. 用 **user-space `xvfb-run`**
4. 並在 **sandbox 外** 啟動 IGV

也就是：

> `slim template + per-locus IGV process + user-space xvfb + sandbox 外執行`

這比「單一 IGV Java process 載入很多 session」更穩，也比「依賴桌面 X session」更可重現。

## 1. 已驗證的環境結論

### 1.1 代理執行環境

| 路徑 | 可否成功 | 穩定性 | 備註 |
|---|---|---|---|
| sandbox 內直接跑 IGV + 桌面 DISPLAY | 不建議 | 低 | 容易受當下 X session 影響 |
| sandbox 內用 user-space `xvfb-run` | 不可行 | 無 | `Xvfb` 無法建立 X11 socket |
| sandbox 外用 user-space `xvfb-run` | 可行 | 高 | 本輪已實測成功 |
| sandbox 外用桌面 DISPLAY | 可行 | 中 | 可出圖，但依賴桌面狀態 |
| 單一 batch / 單一 Java process 載多個 session | 可行但不穩 | 中低 | 容易累積到 OOM |
| per-locus runner，每個 locus 一個 IGV process | 可行 | 高 | 本輪最推薦 |

### 1.2 關鍵判讀

1. 問題核心不是 `sudo`。
2. `xvfb` 可以不靠 `sudo install`，改用 user-space 安裝。
3. 真正卡住 sandbox 內執行的原因，是 `Xvfb` 在該環境無法建立 X11 listener。
4. 因此代理若要穩定自動截圖，**產生 session/batch 可留在 sandbox 內，真正跑 IGV 必須切到 sandbox 外**。

## 2. 標準作業流程

## 2.1 第一次設定：安裝 user-space xvfb

使用：

```bash
scripts/analysis/install_xvfb_user_space.sh \
  --target /home/liaoyoyo2001/.local/opt/xvfb-user
```

這支腳本會：

1. 用 `apt download xvfb` 抓 `.deb`
2. 用 `dpkg-deb -x` 解包到指定目錄
3. 不修改系統套件，不需要 `sudo apt install`

安裝完成後，主要路徑是：

- `Xvfb`：`/home/liaoyoyo2001/.local/opt/xvfb-user/usr/bin/Xvfb`
- `xvfb-run`：`/home/liaoyoyo2001/.local/opt/xvfb-user/usr/bin/xvfb-run`

## 2.2 準備 template

### 推薦

優先使用 **slim template**，不要直接拿肥大的原始 `template.xml` 長批次跑。

現成 slim template：

- `/big8_disk/liaoyoyo2001/InterSubMod/docs/reports/validated/2026/03/assets/20260316_subclone_phase4_igv_sessions/template_hcc1395_subclone_slim.xml`

若要重新產生：

```bash
python3 scripts/analysis/build_hcc1395_subclone_igv_slim_template.py \
  --input-xml /big8_disk/liaoyoyo2001/IGV_session/template.xml \
  --output-xml /big8_disk/liaoyoyo2001/InterSubMod/docs/reports/validated/2026/03/assets/20260316_subclone_phase4_igv_sessions/template_hcc1395_subclone_slim.xml
```

### 為什麼要 slim

因為它已驗證可把 template 從：

- `23 resources / 11 panels`

縮成：

- `9 resources / 3 panels`

這會直接降低：

1. session 載入時間
2. Java heap 累積壓力
3. 遠端 annotation track 對批次穩定性的影響

### 若目標是「忠實保留 template 內容、格式、樣本順序」

可以，而且目前腳本本來就是這樣設計。

`scripts/analysis/igv_snapshot_from_template.sh` 目前只會改兩件事：

1. `Session locus`
2. 每個 alignment track 的 `groupByPos`

其餘內容都直接沿用原始 XML，不會重排 panel、track 或 sample 順序。

也就是說，若你直接指定：

```bash
--template-xml /big8_disk/liaoyoyo2001/IGV_session/template.xml
```

則輸出的每一個 per-locus session 都會保留：

1. 原始 panel 順序
2. 原始 track 順序
3. 原始樣本排列方式
4. 原始 coverage / alignment / feature 的上下層關係

這種模式適合：

1. 想完整保留你平常在 IGV 中熟悉的閱讀順序
2. 想讓批次 PNG 和手動打開 `template.xml` 的視覺邏輯一致
3. 想在 Markdown 中用固定 panel 語意寫觀察說明

### full template 與 slim template 的差別

| 模式 | 優點 | 代價 | 適合情境 |
|---|---|---|---|
| full template | 完整保留原始內容、樣本、panel 順序 | 較慢、較吃記憶體、遠端 track 變因較多 | 正式比對、教學、需要完全對齊既有 IGV 視覺習慣 |
| slim template | 穩定、快、較不易 OOM | 少了部分輔助 track | 批次大量截圖、快速 review、固定 case study 輸出 |

## 2.2.1 原始 template 的閱讀順序

以 `/big8_disk/liaoyoyo2001/IGV_session/template.xml` 目前內容來看，panel 可分成以下幾組：

1. `DataPanel`
   - `removed_fp / removed_tp / kept_fp / kept_tp`
   - 用來先看該位點在既有分類中的上下文
2. `LongPhase-S tumor tagged BAM`
   - `longphase_somatic_output_ssrs` 的 coverage + alignment
   - 偏向看 somatic haplotag 結果
3. `主 tumor BAM`
   - `/big8_disk/liaoyoyo2001/data/bam/HCC1395_Tmode_tagged_ClairS_pileup_v040_woFilter.bam`
   - 是 paired 5kHz 主觀察軌
4. `主 normal BAM`
   - `/big8_disk/liaoyoyo2001/data/bam/HCC1395BL_ONT_5khz_simplex_5mCG_5hmCG_tagged.bam`
   - 用來對照 normal 相位與背景
5. `Dorado tumor / normal 對照`
   - 用於跨平台方向比較
6. `expanded tumor / normal alignment`
   - 給需要看 read 細節時用
7. `SEQC2 / phase VCF / feature panel`
   - 參考序列、truth set、caller 結果與 annotation

### 建議從上到下的觀察法

1. 先看 `DataPanel`
   - 判斷這個位點原本屬於 kept / removed / tp / fp 哪一類
2. 再看主 `tumor BAM`
   - ALT 與 REF 在 read-level 是否可視覺分開
   - `HP` 分群與甲基色塊是否一致
3. 再看主 `normal BAM`
   - normal 是否只有 germline phase 背景，沒有對應 tumor 才有的異常樣式
4. 若要比平台，再看 `Dorado` 對照 panel
   - 只比較方向，不先做定量硬判
5. 最後看 `FeaturePanel`
   - 確認 caller/SEQC2/鄰近 INDEL/MNP/annotation 上下文

### 每一層的意義

| 面板 | 主要問題 | 典型判讀 |
|---|---|---|
| DataPanel | 這位點原本在分類裡屬於什麼 | 是 TP/FP/kept/removed 的哪一種 |
| tumor BAM | read-level 是否真有 allele / HP / 甲基結構差 | ALT 是否成群、是否混在 REF 中 |
| normal BAM | 背景 germline phase 是否已存在 | 區分 tumor-specific 與 germline 背景 |
| Dorado panel | 平台間是否方向一致 | 看現象是否只在 5kHz 出現 |
| FeaturePanel | truth / caller / annotation 是否支持 | 判斷 INDEL adjacency、MNP、HC region、附近變異 |

## 2.3 產生 per-locus session 與 manifest

使用：

```bash
scripts/analysis/igv_snapshot_from_template.sh \
  --template-xml /big8_disk/liaoyoyo2001/InterSubMod/docs/reports/validated/2026/03/assets/20260316_subclone_phase4_igv_sessions/template_hcc1395_subclone_slim.xml \
  --regions /path/to/case_regions.tsv \
  --output-dir /path/to/igv_output \
  --padding 1000
```

這一步會產生：

1. `sessions/*.xml`
2. `igv_batch.txt`
3. `igv_snapshot_manifest.tsv`
4. `snapshots/` 目錄

### region 檔案格式

推薦格式：

```tsv
label	chr	pos	ref	alt
TP_01	chr6	145444893	G	A
```

### 視窗建議

| 用途 | 建議 padding |
|---|---|
| 先快速定位 SNV 附近 read pattern | `1000` |
| 需要看遠一點的甲基結構或鄰近變異 | `2000` |
| 只是確認 target base 與 HP 標記 | `200` 或 `500` |

目前 phase4 case study 建議預設是 `±1000 bp`。

## 2.4 真正出圖：用 per-locus runner

使用：

```bash
scripts/analysis/run_igv_snapshots_per_manifest.sh \
  --manifest /path/to/igv_output/igv_snapshot_manifest.tsv \
  --use-xvfb always \
  --xvfb-run /home/liaoyoyo2001/.local/opt/xvfb-user/usr/bin/xvfb-run
```

### 這是目前最推薦的原因

1. 每個 locus 都會啟動一個新的 IGV process
2. 不會像單一 Java process 一樣把前面載過的 session 累積到記憶體
3. 即使 IGV 仍印出 `reloadSessionItem` 的 UI null-pointer，也通常能正常出圖並結束

## 2.4.1 若想用原始 template 固定內容直接批次出圖

使用：

```bash
scripts/analysis/igv_snapshot_from_template.sh \
  --template-xml /big8_disk/liaoyoyo2001/IGV_session/template.xml \
  --regions /path/to/case_regions.tsv \
  --output-dir /path/to/igv_output_full_template \
  --padding 1000

scripts/analysis/run_igv_snapshots_per_manifest.sh \
  --manifest /path/to/igv_output_full_template/igv_snapshot_manifest.tsv \
  --use-xvfb always \
  --xvfb-run /home/liaoyoyo2001/.local/opt/xvfb-user/usr/bin/xvfb-run
```

這樣輸出的 PNG，內容與 panel 排列會盡量貼近你直接打開 `template.xml` 的視覺順序。

## 4. 參數建議

## 4.1 `run_igv_snapshots_per_manifest.sh`

### 推薦預設

- `--use-xvfb always`
- `--xvfb-run /home/liaoyoyo2001/.local/opt/xvfb-user/usr/bin/xvfb-run`
- `--sleep-ms 1500`
- `--max-panel-height 5000`

### 何時要調整

| 參數 | 何時調整 | 建議 |
|---|---|---|
| `--sleep-ms` | remote track 載太慢、snapshot 太早截 | 改成 `2500` 或 `3000` |
| `--max-panel-height` | track 太多、圖被壓縮 | 改成 `6000` 或 `8000` |
| `--start-port` | 同時跑多批避免 port 衝突 | 換成另一段，例如 `60200` |

## 4.2 `igv_snapshot_from_template.sh`

### 推薦預設

- `--padding 1000`
- 不要直接 `--run`
- 先產生 manifest，再交給 per-locus runner

### grouping / sorting

這支腳本支援額外的 batch grouping / sorting，但目前不建議預設打開。

原因：

1. template 已可保存既有 track / alignment 設定
2. 多加 batch 指令會增加 debug 成本
3. 若要固定用 `HP` 分群，應先確認 session 中的對齊顯示與 tag 一致

只有在明確需要時才加：

```bash
--group-mode tag --group-arg HP
```

## 4.3 `igv.sh` / Java 參數

目前 `/home/liaoyoyo2001/igv.sh` 內建是：

- `-Xmx8g`

而且支援讀：

- `~/.igv/java_arguments`

### 目前結論

1. **不需要先修改 IGV Java 參數，才能讓流程可用**
2. 真正提高穩定性的主因是：
   - slim template
   - per-locus runner
   - sandbox 外的 user-space xvfb
3. `-Xmx8g` 對 slim template + per-locus 目前已足夠

### 何時才建議調整 `-Xmx`

若遇到以下情境，才考慮在 `~/.igv/java_arguments` 增加記憶體：

1. template 又變肥
2. 一次要載更多 BAM / VCF / annotation
3. 必須改回單一 Java process 長批次

例如可放：

```text
-Xmx12g
```

或：

```text
-Xmx16g
```

但在目前架構下，**優先順序是先瘦 template，不是先把 Java heap 一直加大**。

## 5. 已知問題與處理方式

## 5.1 `reloadSessionItem` null-pointer

IGV batch 模式在 `load session` 時，會看到：

- `reloadSessionItem` 的 `NullPointerException`

目前觀察：

1. 這個錯誤在 per-locus runner 下仍可能出現
2. 但單 locus process 通常仍會完成 snapshot 並正常結束
3. 因此它是 **已知可接受噪音**，不是目前主阻塞

## 5.2 遠端 track 造成不穩

原始 template 含有遠端：

- `Refseq Select`

這會增加：

1. 載入等待時間
2. 網路依賴
3. batch 失敗變因

因此建議：

1. 若是正式批次，優先用 slim template
2. 若不需要 gene annotation，就不要把遠端 track 放回去

## 5.3 舊 script 不建議再作為主入口

舊版：

- `/big8_disk/liaoyoyo2001/InterSubMod/scripts/utils/igv_batch_screenshot.sh`

問題：

1. 假設系統已安裝 `xvfb-run`
2. 沒有 per-locus process 隔離
3. 沒有 manifest/session 的中間層可以重跑與追蹤

因此後續請以 `scripts/analysis/` 下面這三支為主：

1. `build_hcc1395_subclone_igv_slim_template.py`
2. `igv_snapshot_from_template.sh`
3. `run_igv_snapshots_per_manifest.sh`

## 6. 最終建議

未來只要是 IGV 自動截圖，統一照下面做：

1. 先準備或重建 slim template
2. 產生 per-locus session / manifest
3. 用 user-space `xvfb-run`
4. 在 sandbox 外跑 per-locus runner
5. 若真的遇到 OOM，再考慮調高 `-Xmx`

換句話說，**需要修改的不是 IGV 主參數本身，而是執行策略**。  
真正該固定化的是：

1. `slim template`
2. `per-locus process`
3. `user-space xvfb`
4. `sandbox 外執行`
