## Slide 17: 時間 200s → 40s

Performance & Logic Issues – 投影片摘要版
1. 效能問題（Performance Issues）
1.1 重複開啟 BAM 及反覆讀取 index
問題點：process_single_region() 每次都建立新的 BamReader → 每次都重新讀 .bai 索引
影響：大量 I/O、延遲倍增（區域數量大時更明顯）
建議改善：在 thread 層級建立並重複利用 BamReader或建立 reader pool，避免反覆載入 index
1.2 MatrixBuilder 使用過度複雜的資料結構
問題點：std::map<int, std::map<int32_t, float>>樹狀 map 插入慢、記憶體碎片多
影響：大規模 methylation calls 時效能差
建議改善：改用 std::vector<std::vector<std::pair<int32_t, float>>>更接近連續記憶體、快且操作簡單
1.3 CIGAR 解析被做了兩次
問題點：ReadParser 與 MethylationParser 都各自走一次 CIGAR
影響：每筆 read 成本乘 2
建議改善：建一次 seq_to_ref map，共用給兩者或至少讓 MethylationParser 單獨負責完整 mapping
1.4 反覆分配 seq_to_ref vector
問題點：每筆 read 都 new vector
影響：大量 heap allocation
建議改善：使用 thread-local vectorclear() + resize() 重複使用即可

2. 邏輯與正確性問題（Logic Issues）
2.1 反向鏈（reverse strand）甲基化被忽略
問題點：只在 SEQ 找 'C'，但反向鏈會變 'G'影響：最多可能遺失 50% 甲基化訊號
建議改善：檢查 bam_is_rev(b)若為 reverse：改找 'G'（原本為 C）同時確認 MM tag 對 reverse read 的標註行為Dorado/Guppy 可能對 reverse 做 normalization，需要驗證
2.2 型別不一致
問題點：int32_t、uint32_t 混用
影響：比較、邏輯判斷可能產生 overflow / warning
建議改善：與 HTSlib 一致 → 建議統一用 int32_t
3. 程式品質（Code Quality）
3.1 註解不足
問題點：CIGAR 座標推算邏輯複雜，缺乏必要註解
建議改善：補充「為何這樣做」的英文註解（非僅描述程式碼）
3.2 錯誤處理不明確
問題點：fetch_reads() 失敗與「無讀取結果」回傳一樣
影響：bug 隱性、不易 debug
建議改善：失敗時記錄警告或以 exception 區分

時間 200s → 40s

最大記憶體 9GB → 11GB

## Slide 27: Vibe Coding 開發心得整理

Vibe Coding 開發心得整理

> **Notes:** ## Vibe Coding 開發心得整理

在開始任何開發前，必須先徹底了解整個專案的核心目標，清楚區分哪些功能是「必備」，哪些是「擴充」。同時，提前確認會使用到的套件、資料夾結構、文件書寫格式，以及 Git 版控流程，才能避免後續因方向錯置而返工。

接著，先讓 AI 協助整理並拆分專案架構，將主要模組拆成子項目，並為每一項制定驗證方法，再進一步撰寫成設計文件、開發文件與測試文件。這部分一定要仔細檢查，確認每個步驟沒有偏離主軸，也沒有使用錯誤的方法（這點非常重要）。

在執行開發前，也需要評估每個模型在各項任務中的**信心程度**、**成本**、以及**必要的輸入/讀取量**。開始動工後，要持續觀察 AI 的操作方式與回覆內容是否合理。例如：曾因 AI 未正確讀取甲基化資訊，導致把測試檔案從 tumor 誤改成 normal，必須強制要求使用 tumor，並指出判斷不合理。AI 在重新驗證後才發現問題源自 *MethylationParser* 中 cigar 解讀錯誤，而且類似狀況會反覆出現。這些時候就需要靠經驗去判斷、指證，或透過測試輸出讓 AI 自行發現並修正。

在程式碼審查方面，則需依照子任務的規模與完成度信心，決定檢查的頻率與深度，而非每段都一視同仁。

測試部分則必須讓輸出結果與驗證方式「肉眼可見」，才能快速判斷是否有不合理的地方，同時也能讓 AI 生成無法抉擇的比較列表，作為進一步決策依據。例如：

1. BAM 與 VCF 的 1-base 座標以 `uint32_t` 定義長度與位置，但 SNV 的 0-base 座標應改用 `int32_t`。
2. 處理座標邊界時雖有檢查是否小於 0，但卻忽略了大於染色體長度的情況。

整體感覺，現在使用 AI 開發很像在「當老闆」：
你要決定目標、挑選高 CP 值的“員工”、設定任務、監督進度、確認成果是否符合同預期，最後再評估效益。

重新讓 AI 再寫一次程式，就像重新創業一次：可以減少很多彎路，並在一開始就預先防範與解決那些舊問題。
