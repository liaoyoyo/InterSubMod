一眼總覽

做得好你的操作方式像一位抱持懷疑態度的 PI，而非只想要快速答案的人——你要求量化、源頭可追溯的驗證，請 Claude 計算 ceiling math、跑跨樣本 ablation，當特徵無法泛化時願意接受誠實的負面結果。你還建立了可複用的方法學層（scientific-rigor skill、LLM-direct HTML 報告 pipeline），把最佳實踐變成可強制、可重複的工作流。

阻礙Claude 側：產生的腳本有時夾帶細微 bug（falsy-zero、計數錯誤、型別不符），且棄用 build flow 曾覆寫手動 commit 的 HTML——研究情境中靜默錯誤會污染結論。你側：長時間分析與大型 fan-out 反覆撞 output-token / rate limit，使整個 session 只剩錯誤訊息；切成更小 checkpoint 並 commit 中間結果可少丟 context。

速贏你已在建 Custom Skills——進一步用 Hooks 自動擋棄用 flow、在腳本執行前驗證它。對抗式稽核與文件 fan-out 改用 Task Agents 在隔離 context 跑聚焦平行審查，避開 rate limit 逼出的逐筆 re-audit。

野心工作流嚴謹優先的習慣讓你有條件跑自主「假說→裁決」迴圈：agent 自己找資料、預先註冊計劃、跑 LOSO / 跨樣本 ablation、附數學給可辯護的 GO/NO-GO。再搭配自我稽核的 TDD refactor 群：寫隔離測試、一次一 commit 修 bug、絕不覆寫已 commit 工作。

二、互動風格

你的運作方式像一位嚴謹至上的研究科學家，把 Claude Code 當抱持懷疑的協作者與對抗式審查者，而非單純 coding 助手。最鮮明的特質是堅持驗證：一再要求 verify / validate / audit，對照真實資料與源碼，而非接受聽起來合理的答案。甲基化/ISM 的 F1 調查清楚展現——你不是要「加特徵」，而是要決定性的 ceiling math、AUC 趨勢、跨樣本 LOSO ablation，誠實揭示能否泛化（而當 Claude 説「不能」時你是滿意的）。你甚至打造工具固化這套心態：開發並考核 /scientific-rigor skill（evidence levels + Hard Gate），並要求 Claude 在全規模評估前先建議「別急、改用 pre-registration」。

關鍵模式：你把 Claude 當對抗式科學審查者來驅動，要求源頭可追溯的驗證與誠實的負面結果，勝過附和。
比起得到認同，你更看重被告知「不，資料不支持這個」。

三、有效運作的部分

嚴謹優先的假說驗證

一貫要求量化、源頭可追溯的驗證：算 ceiling math、跑跨樣本 LOSO ablation、揭露自己 ISM/甲基化特徵的 circularity。當 filter 特徵跨樣本無法泛化時，得到用真實資料佐證的誠實負面結果，而非討好結果——這正是好科學該有的。

建置 scientific-rigor skill 系統

超越一次性任務，工程化出可複用方法學層：建/壓測含 Hard Gate 邏輯、evidence-level 檢查、pre-registration 建議的 /scientific-rigor skill；考核它並套用到真實決策（是否重開 NO-GO 方向）——把最佳實踐變成可強制、可重複的工作流。

LLM-direct HTML 報告 pipeline

用 model-direct HTML 產生 skill 取代脆弱 Python/PPT pipeline，對照業界實踐驗證、遷移依賴 skill，commit 34 檔。成果是發表級報告（SVG 視覺、anti-overclaim 保護、可對照源碼驗證），透過快速迭代精修產出。

四、問題分析

1API token 與 rate limit 打斷工作

許多 session 撞 500 output-token 上限或 server 端 rate limit，整份 transcript 只剩錯誤訊息，被迫中途 compact/重啟。建議切小 checkpoint、commit 中間結果。

  • 多個 session 完全葬送於 token-limit 錯誤，目標與成果無法復原。
  • 甲基化專案 scoping 在資料夾與工作流建立前，就被 thinking-blocks API 錯誤打斷。

2產生腳本中自己造成的 bug

擷取/插入/分析腳本反覆夾帶 bug，需抓出重跑。多數能自我修正，但拖慢分析循環、有讓結論出現靜默錯誤的風險。

  • falsy-zero bug（p_cis=0.0 被當 falsy）+ 打錯數字（0.142 打成 0.122）混進 catalog 腳本，需重做才能信任。
  • 網站重構時擷取腳本漏 renderMembers.js 的 script tag、因引號不符誤算 reference，需對 21 份文件 inline re-audit。

3棄用工具覆寫已 commit 的工作

過時 build flow 與被擋的 HTML 做法，使手動 commit 的工作被覆寫/拒絕，被迫多步驟復原。

  • 棄用的 build_html.py rebuild flow 覆寫手動 commit 的 HTML、復活已刪 slide，需多步驟復原。
  • hook 擋住 innerHTML、Copy 按鈕在非安全 HTTP context 失效，報告中途需改寫與 fallback。

五、建議

A. 可加入 CLAUDE.md 的內容

① Scientific Rigor：接受任何研究結論前一律套 evidence-level 分級與 Hard Gate；每個量化宣稱對照源碼/資料驗證、明確標記過度宣稱；全規模泛化前建議 pre-registration。（多 session 呼叫此檢查、揭露被誇大宣稱如 BRCA2、抓出無法泛化特徵。）

② HTML Reports：用 model-direct HTML skill；絕不用棄用 build_html.py / python-PPT rebuild（會覆寫手動 HTML、復活已刪 slide）；避免 innerHTML（被 hook 擋）；為 Copy 按鈕提供 HTTP-context fallback。

③ Verification：每個宣稱紮根源頭 artifact、回報前用真實資料驗證、用 anti-overclaim 保護、複查數字謄寫（小心 falsy-zero）。

B. 值得一試的功能

  • Custom Skills：單一 /command 觸發的可複用 prompt。把 scientific-rigor 檢查、HTML 報告、PI murder-board 變 /command 消除重複。
  • Hooks：生命週期事件自動執行 shell。PreToolUse hook 可擋 build_html.py + 編輯前跑 git-status 守衛。
  • Task Agents：聚焦 subagent 平行探索/稽核。多 agent 稽核效果好但 fan-out 撞 rate limit → 改「有界循序」一次稽核一模組。

C. 使用模式

馴服 output token 上限：大型交付切明確批次、要求精簡串流輸出、中間結果寫檔。

以小批次提交工作：一次產一個 section，每段立刻寫到檔案，每次回應都在 output 上限內再進到下一段。

標準化誠實研究敘事：永遠先分級證據、測試泛化，編成 skill 讓每份報告繼承。

定稿此報告前，跑一次 ablation/LOSO 泛化檢查、把每個宣稱按 evidence level 分級、標記任何未被源頭資料直接支持的陳述。

保護 git 工作流中已 commit 的工作：破壞性編輯前 git status、確認無並行 session、偏好版本遞增而非原地 rebuild。

編輯任何已 commit 的 HTML 前，先跑 git status、確認工作樹乾淨、建一個版本遞增而非原地 rebuild。

六、未來展望

自主「假說→裁決」研究迴圈

agent 接收原始假說 → 定位資料 → 跑 ablation/LOSO/跨樣本驗證 → 回傳帶 ceiling math 與 AUC 趨勢的決定性 GO/NO-GO，全程不需手動編排。預先註冊計劃、揭露 circularity、拒絕過度宣稱，像懷疑的 PI。把數週手動評估變成一夜跑、誠實泛化。

自我稽核的 TDD codebase Refactor agent 群

多 agent 對抗稽核 C++/Python codebase 方法學瑕疵、寫隔離測試重現 bug、一次一 commit 修正並留 provenance；出貨前抓自己的 falsy-zero / 型別不符；以耐心等待化解跨 session git 衝突。把高風險手動 refactor 變 TDD-gated、完全可追溯、絕不覆寫已 commit 工作。

源頭紮根的報告與簡報 pipeline

直接由模型產發表級 HTML/SVG 報告與簡報，紮根驗證過的 artifact、內建 anti-overclaim。盤點素材、對照源碼驗證每宣稱、跑內部 murder-board、迭代敘事——產 committed/有版本、能挺過 PI 級審視的交付。用單一 LLM-direct skill 取代脆弱 Python/PPT，從「17:1 偏差說明圖」擴展到多支柱論文 deck。
