# 最終報告證據與章節映射：Verification v2／RegionStratifier 修復

> **TL;DR — 最終報告可以完整敘述 P0/P1 的規格、實作、consumer 與 fail-closed 證據；living notes 已記錄 P2 frozen-corpus formal publish 為 14/14 VALID，但在輸出 manifest、status、逐檔報告與獨立 validator 直接綁定到報告前，這個 P2 結果只能列為 L2「已報告」，不得升為 L1 獨立驗證結論（影響：高；信心：高）。**

**敘述框架：SCQA（Situation → Complication → Question → Answer）＋ Claim–Evidence–Reasoning。** 本文件是最終 HTML 報告的 evidence map，不是 P2 執行紀錄，也不是科學生物學驗證報告。

## 0. 文件定位、任務分類與使用規則

| 項目 | 決定 |
|---|---|
| 任務類型 | **(E) Hotfix/Bugfix + (B) Comprehensive validation**；P0/P1 修復可由單元與整合證據支持，P2 則必須涵蓋 frozen 14 檔全 scope |
| 服務目標 | **G4** 多樣本一致性與 reproducibility；**G5** 可由外部 reviewer 重跑與驗證的業界級證據鏈 |
| Evidence court | authoritative spec 定義驗收契約；source maps／ledger 定義已實作或已盤點狀態；frozen manifest 定義不可漂移的輸入；P2 正式輸出才可證明 migration 結果 |
| 本文件可做 | 建立章節順序、claim tier、證據路徑、限制、禁止用語與 P2 正式填寫欄位 |
| 本文件不可做 | 代替 P2 migration、代替正式 validator、代替 biology truth、代替 F1／precision／recall benchmark |
| 當前交付狀態 | Evidence map 可供 final report writer 使用；P2 在 living notes 已有 reported result，但所有 `P2_*` formal fields仍需從正式 artifacts逐欄綁定 |

### 0.1 L1–L5 證據等級

本文件將不同來源原有的 `L1/L2/RISK` 標記統一映射成下列 final-report 等級，避免同一個「L2」在不同文件代表不同含義：

| Tier | 本文件定義 | 可使用語氣 |
|---|---|---|
| **L1** | 直接、可定位、可重算的規格／source／manifest／ledger 證據；關鍵欄位有精確值或逐列紀錄 | 「定義為」「實作為」「ledger 記錄為」 |
| **L2** | 有主要證據，但缺少原始 durable log、獨立重演或其中一段邊界仍未直接測試 | 「已有支持，但限制為……」 |
| **L3** | 由 source order、failure path 或 bounded inventory 推導的合理推論 | 「可推論」「預期」，並同句標明未直接驗證 |
| **L4** | 尚待正式執行、外部 ABI 檢查或 P2 artifact 才能決定 | 「待驗證」「不得提前宣告」 |
| **L5** | 與現有證據衝突，或已知不能由本 evidence court 支持 | 不可作正面結論；只可列為矛盾／禁止 claim |

### 0.2 Claim 使用 gate

1. Final HTML 的每個關鍵結論都要帶 claim ID 與 tier。
2. 同一 claim 若同時有 code-level 與 corpus-level 層次，必須拆成兩個 claim；不可用 C++ 單元測試或 living-notes摘要替代 frozen-corpus formal artifacts。
3. `EXPECTED` 是規格目標，不等於 `OBSERVED`；P2 欄位完成前，兩者必須使用不同表格。
4. QA_REPORT 只證明規格／manifest artifact QA，不證明 biology、upstream truth 或 post-fix production run。
5. 報告若使用「全量」「VALID」「完成」三個詞作 L1 verdict，必須先通過 §6 的 P2 formal evidence gate；在此之前只能精確寫成「implementation notes 記錄為……（L2）」。

## 1. SCQA 主敘事與章節骨架

### 1.1 Situation

InterSubMod Stage④ 原本需要把 legacy 4-class Verification 決策升級為 ordered 11-class v2，同時使 RegionStratifier 的 eligibility、stratum precedence、fixed-slot 狀態、class counters、LOH provenance 與 downstream contracts 都能精確重現。規格同時凍結 14 份 CSV、共 328,697 data rows，作為 P2 schema-only migration 的完整驗收 corpus。

### 1.2 Complication

修復前風險不是單一欄位名稱問題，而是多層 contract 漂移：Stage④ class split 與 precedence、`n_subclones` 語義、current/legacy counter 混用、LOH provenance、stale valid-looking artifacts、consumer 直接解讀舊字串，以及 migration 可能產生部分覆寫。C++ 單元測試即使全綠，也不能自動證明 14 檔每列 stable-key、raw token 與 `Significant` invariance。

### 1.3 Question

最終報告必須回答：

1. 每個判斷從哪一個 input field 進入、依何種 exact predicate／precedence 得到哪個 output？
2. 何時 fail closed、何時允許 publish、何時只能保留 FAILED／RUN_IN_PROGRESS？
3. compatibility aliases 與 downstream consumers 如何遷移，還有哪些外部／歷史風險？
4. 哪些結果是 source-level 已證，哪些必須等 P2 formal artifacts 才能宣告？

## 2. 方法與判斷設定：Final HTML 必須逐項呈現

### 2.1 Stage④ ordered 11-class v2

Final HTML 不得只列 class 名稱；至少要顯示 predicate、precedence、evidence path 與 `Significant`：

| Order | Exact predicate | Current class | EvidencePath | Significant | Claim |
|---:|---|---|---|---:|---|
| 1a | cluster-first support 且 legacy `Strong` | `Strong_Bidirectional` | `BIDIRECTIONAL` | true | C03–C05 |
| 1b | cluster-first support 且 legacy `Subclone` | `ClusterFirstOnly` | `CLUSTER_FIRST_ONLY` | true | C03–C05 |
| 2 | `potential_loh && (hp_auc_struct || dbeta_sig)` | `LOH-Structure` | `LOH_STRUCTURE` | true | C03–C05 |
| 3 | `within_hp` | `MultiGroupNoLabel` | `WITHIN_HP_MULTIGROUP` | true | C03–C05 |
| 4 | `dbeta_sig` | `LabelShift` | `LABEL_SHIFT` | true | C03–C05 |
| 5 | `clean_location_permanova` | `PermanovaLocation` | `PERMANOVA_LOCATION` | true | C03–C05 |
| 6 | `hp_auc_struct` | `StructureNoLabel` | `HP_AUC_STRUCTURE_NO_LABEL` | true | C03–C05 |
| 7 | `dispersion_structure` | `DispersionStructure` | `DISPERSION_STRUCTURE` | false | C03–C05 |
| 8 | `pairwise_mean_distance < 0.15` 或 non-NaN `epipoly_hp1 < 0.2` | `Noise_Uniform` | `NOISE_UNIFORM` | false | C03–C05 |
| 9 | non-NaN `epipoly_hp1 > 0.5` 或 `pairwise_mean_distance > 0.35` | `Noise_Chaotic` | `NOISE_CHAOTIC` | false | C03–C05 |
| 10 | 以上皆未命中 | `Noise_Uncorrelated` | `NOISE_UNCORRELATED` | false | C03–C05 |

不可省略的 edge semantics：

- `0.15`、`0.2` 不命中 uniform；`0.5`、`0.35` 不命中 chaotic，因 predicate 是 strict `<`／`>`。
- `epipoly_hp1=NaN` 時跳過兩個 epipoly predicates。
- precedence 是 first-match：cluster → LOH → within-HP → Δβ → clean PERMANOVA → HP-AUC → dispersion → uniform → chaotic → uncorrelated。
- `LabelFirstSupport = legacy in {Strong, Weak}`；`ClusterFirstSupport = legacy in {Strong, Subclone}`。
- `WithinHPSupport` 與 `DispersionWarning` 來自 live Stage④ axes；`EvidenceDerivation` 的 live default 是 `LIVE`。
- `SuggestFilter` 是獨立 legacy 欄位，不可與 v2 `Significant` 混為一個 gate。

### 2.2 RegionStratifier

唯一 eligibility predicate：

```text
result.success
&& result.num_reads >= 10
&& result.num_cpgs >= 3
&& result.significance_computed
```

`verification_significant=true` **不是** eligibility 條件；這一點必須在 final HTML 明示，避免只保留 positive classes。

| Precedence | Predicate | ID | Label | Reason |
|---:|---|---:|---|---|
| 1 | `potential_loh || loh_bed_overlap` | 2 | `LohFlagged` | `LOH_FLAGGED` |
| 2 | `abs(sample_asm_delta) > 0.10` | 3 | `HighSampleAsm` | `HIGH_SAMPLE_ASM` |
| 3 | `abs(hp_asm_delta) > 0.05` | 1 | `HighHpAsm` | `HIGH_HP_ASM` |
| 4 | otherwise | 0 | `BaselineLowAsm` | `BASELINE_LOW_ASM` |

Boundary／state requirements：

- `0.05` 與 `0.10` 本身仍是 baseline；`0.050001`、`0.100001` 才跨過門檻。
- default minimum eligible regions 是 50：0→`INSUFFICIENT_REGIONS/NO_ELIGIBLE_REGIONS`；49→`INSUFFICIENT_REGIONS/BELOW_MIN_REGIONS`；50 才能進 VALID path。
- storage 永遠有 4 fixed slots；occupied count 依實際出現的 unique IDs 計算。
- deprecated `n_subclones` 是 `n_occupied_region_strata` exact mirror，不是細胞 clone 數。
- current v2 counters 接受 11 leaves 且要求 schema version 2；legacy counters只接受 4 leaves；unknown 進獨立 counter，不可 silent fallback 到 Noise。
- dominant class ties 依固定 array order以 `;` 串接，不能以 hash iteration order 決定。

### 2.3 LOH provenance

Final HTML 應畫出單向鏈：

```text
pre-v2 verification class
  → verification_class_legacy snapshot
  → determine_loh_subtype_legacy_vc(potential_loh, legacy class)
  → LOH_Subtype_LegacyVC (canonical)
  → LOH_Subtype (deprecated exact alias)
```

合法輸出為 `None` 或依四種 legacy class 對應的 LOH subtype；unknown legacy 必須 fail closed，不能即使 `potential_loh=false` 就偷偷降成 `None`。

### 2.4 Publication 與 status

Final HTML 必須區分三個層次：

1. **Assignment commit**：complete-set validator 通過後才寫回 `RegionResult`，validator 失敗時零 partial mutation。
2. **單檔 publication**：建立 temp、寫入、flush、close、validate，最後 rename；TempFileGuard 負責 failure-path cleanup。
3. **整批 status**：預先寫 `RUN_IN_PROGRESS`／失敗時寫 `FAILED`；只有全部必要 artifact durable後才寫terminal VALID status。P2 output SHA由獨立output manifest承載，不可誤說成C++ 9-column status內建digest欄。

不可把「每個 artifact 原子 rename」說成「所有 artifacts 與 status 是單一跨檔 transaction」。這是已知邊界，應在風險章保留。
