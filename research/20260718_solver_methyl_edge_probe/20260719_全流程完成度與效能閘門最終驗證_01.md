# 全流程完成度與效能閘門最終驗證

## 1. 任務分類與研究邊界

- Task type：**B — Comprehensive validation**。
- 服務目標：**G3**（read-level epigenetic/abundance layer）與 **G5**（可由外部重驗的 exact/fail-closed 工程證據）。
- Thread D：相關；VAF/read-AF ranking 是 read-level abundance evidence。
- Thread B 撤回範圍：不相關。
- KDE-corrected：本次 structural pattern replay 與 BQ-aware likelihood 不使用 KDE，故不適用。
- VCF caller AF：本次不使用 merged AF 或 caller AF；VAF probe 綁定現行 BQ-aware read-pattern mixture likelihood。
- 長計算：是；hard25 僅在 declared conflict process/root 都為 0 的資源閘門後啟動。

本報告刻意區分三個不同端點：

1. **Controller completion**：每個 worker 都回傳 complete 或明確 incomplete 狀態。
2. **Family completion**：每個 structural key 的所有最簡 vertex sets 均已列完。
3. **Ranking completion**：所有必要候選均評分，且完整最佳/tie class 可安全發布。

只有第 1 項全部完成；第 2、3 項尚未全部完成。

## 4. 可以說的加速與不能說的加速

### 4.1 可確認：三個同端點 complete cases 有顯著診斷加速

| 範圍 | Solver speedup | Isolated process speedup |
|---|---:|---:|
| 最小 | 63.17× | 16.39× |
| 中位數 | 90.55× | 42.11× |
| 最大 | 263.04× | 69.49× |
| 三案合計 | 125.05× | 43.01× |

這三案同時滿足 current/optimized 都 complete，且 objective、family count與digest一致，因此比較的是相同科學端點。限制是 `n=3`、單次、固定 current-first，只能稱為 **paired-complete diagnostic**。

### 4.2 不可宣稱：hard25 或 production 的整體完成加速

- Current observed wall（含 deadline-censored）=`703.769 s`。
- Optimized observed wall（含 deadline-censored）=`327.540 s`。
- 表面比值約 `2.149×`，但兩邊都含 incomplete runs。
- Receipt 因此正確標記：
  - `reported_ratio_kind=NOT_COMPARABLE`
  - `reported_current_over_optimized_ratio=null`
  - `total_completion_time_speedup_current_over_optimized=null`

所以 **2.149× 不是 completion speedup**，不能作論文或 production 效能宣稱。

### 4.3 Exact counter 很快，但它是不同端點

- HCC hard examples可在短時間直接得到 perfect-family counts：
  - `104,640`
  - `122,281,152`
  - `27,360`
- H1437/H2009 historical-v5 panel：208/208均有 total status；186 exact、22 recurrence abstain。
- Cross-sample count runner約 `1.146 s`，counter sum約 `0.448 s`。

這證明「不列出每棵樹，只計算總數」可以大幅壓縮；但它沒有輸出每棵樹，也沒有完成 VAF ranking，因此不能和 explicit family completion直接互換。

## 5. 為何仍無法全部完成

主要瓶頸不是最低 objective，而是最佳解集合本身太大：

- 6 個 optimized incomplete perfect cases的最簡 family counts為  
  `104,640；122,281,152；27,360；72,576；2,680；9,408`。
- 另 3 個 cases需要 recurrence-aware family method；目前 perfect counter明確 abstain。

若輸出合約要求逐棵列出 \(F\) 個候選，光是寫出結果就有 \(\Omega(F)\) 下界；若每棵還需執行一次 likelihood fit，最壞時間為：

\[
\Theta\!\left(F \times \mathrm{Fit}(m,n_{\mathrm{patterns}})\right).
\]

因此，限制 \(k\) 只能限制 hypercube 的理論輸入規模，不能保證候選 family 很小，也不能保證 deadline 內全部列完。相同 \(k\) 下，read constraints不同仍可從唯一解到上億個同層最佳解。

## 7. 最終 GO/NO-GO

### 已通過

- Resource gate false-negative修補。
- R3 frozen authority、cross-sample frozen panel與 source binding。
- Exact objective、perfect-family count與 recurrence abstention。
- Current/optimized 的小型 complete-family correctness。
- Candidate cap/deadline/tie cap/incomplete ranking 的 fail-closed。
- m≤5 compressed VAF full-enumeration oracle。

### 未通過

- Optimized hard25 family completion：9/25 incomplete。
- 所有 controls成對 complete。
- 25-key overall completion speedup。
- Recurrence-aware family count/enumeration。
- Machine-certified numerical pruning與 hard process watchdog。
- 所有 hard cases的 VAF/read-AF ranking。

### 決策

**NO-GO_PRODUCTION。**  
不啟動 production adapter、雙 actual-data pilots與 full 154；這不是漏跑，而是 comprehensive validation gate失敗後的正確停止行為。

## 8. 要達到「全部可完成」所需的最短改良順序

1. 實作 `excess=1` recurrence-aware count/traceback DP，先涵蓋目前 3 個 abstain cases。
2. 將 top-level branch probe改成 recursive DP-state branch-and-bound。
3. 對 likelihood upper bound加入 outward-rounded interval certificate；否則剪枝只能 diagnostic。
4. 加入外層 subprocess watchdog，使 deadline涵蓋 DP、branch建構與 optimizer。
5. 定義 exact compressed output contract：例如 exact count＋best score＋可證 tie class；若仍要求列出上億個 tree IDs，就無法消除 \(\Omega(F)\) 輸出成本。
6. 重跑 interleaved、多 repeats hard25；只有 25/25 complete且同端點 correctness全通過後，才進入雙 actual-data pilots與 full 154。
